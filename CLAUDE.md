## Review gates — scale to irreversibility

- Architecture, trust boundaries, cryptographic design, anything to be published: full adversarial rotation before implementation.
- Benchmark harnesses, measurement code, throwaway spikes: **build immediately**. The artifact self-verifies against test vectors and a review round adds nothing. `tools/check-amendments.ts` is in this category.

**Two rounds is the right number for a throwaway spike, and the second round reviews the FIXES.** Learned 2026-08-18 and worth not rediscovering. Round one found a defect the code had. ## Keys

~~Never write ElGamal keygen code before the Cryptography Reviewer has ruled on ADR-0001 §(e).~~ **Ruled 2026-08-18, implemented and executed 2026-08-20.** The construction lives in `docs/reviews/REVIEW-012-RULING-keygen-2026-08-18.md` and **only** there — do not paraphrase it into the ADR or the architecture document. `signer/src/keygen.rs` is an *implementation* of that prose and says so; where the two disagree, the ruling wins. Derivation from the XRPL master seed is upheld, with five conditions.

**Three things about that ruling that a coding session will otherwise get wrong:**

- **Its reduction is TOTAL and has no abort path**, unlike the sigma-nonce and `r`/`ρ` rulings, which both say *abort on zero, never retry*. That is correct there, where the input is fresh entropy and an abort costs one transaction. Keygen's input is a **fixed seed**, so an abort would be permanent — that holder could never participate. Do not "fix" it back.
- **Condition 2 is not cosmetic.** Onboarding must disclose that the master seed becomes a permanent decryption credential, and the signer must **warn** when the account carries `lsfDisableMaster`, a regular key or a signer list (E-69). For those holders the master seed is not spending authority, and §(e)'s argument for derivation does not hold.
- **The registration PoK must always be passed a non-NULL `context_id`.** The library accepts NULL and then emits an account-unbound, replayable proof (F-19). rippled cannot reach that path; our signer can.

~~When keygen is written, validate it against~~ **Done 2026-08-20.** mpt-crypto's own tests — `test_pok_sk`, `test_elgamal`, `test_elgamal_verify` — are C programs over **random** keys, so `signer/tests/keygen_interop.rs` drives their *properties* with a derived key. **Necessary, not sufficient:** a constant `sk_A = 1` passes all three, and **that claim is now itself a test** — `a_constant_sk_of_one_passes_every_upstream_check` runs it and asserts they pass, which is what makes the KAT load-bearing rather than decorative. ## Testing

Every capability claim needs a test that fails if the claim is false.

For confidentiality specifically, **a demo of the happy path is not evidence of confidentiality.** Two harnesses are required:

- **Observer harness** — shows exactly what a full-ledger observer sees. Its first test is finding F-1 in `CLAIMS.md`: recompute the canonical `EncZero` independently and check whether freshly-initialised and post-merge balances are publicly identifiable as zero.
- **Issuer-view tool** — a single CLI command (`tools/issuer-decrypt-balance.ts`) that reads one account's `sfIssuerEncryptedBalance` and decrypts it given the issuer key. Not a standalone application. Showing what the issuer sees is the honest counterpart to showing what the public sees.

## Capturing upstream feedback

This project produces a second output alongside the artifact: observations for the RippleX teams working on privacy and confidentiality. Capture is a coding-session job because friction is only visible at the moment you hit it — an error code that does not say which proof failed, a field the docs describe wrongly, a build step nothing warns you about. By the next session it reads as normal and you stop noticing.

When you hit one, add a row to `UPSTREAM-FEEDBACK.md` under `Observed`, with what you were doing and what you expected. Do not grade it, do not write it up, do not decide whether it is worth sending. Capture and move on.

**Two slash commands carry the procedure**, because this is a repeated task and not a project convention: **`/upstream-issue`** drafts a filing from a finding, **`/issue-review`** attacks the draft before it is sent. ⚠ **User-invoked, in `.claude/commands/` beside the other three** — never model-invoked, because filing needs the owner's authorisation every time. ⚠ **Run `/issue-review` before every filing** — protocol rule 1 gates on it.

⚠ **The first thing either skill does is read the TARGET repository's own issue template**, and that is not a formality. **Measured 2026-09-01: `XRPLF/rippled` sets `blank_issues_enabled: false` and offers only `bug_report.md` and `feature_request.md`.** `rippled#8118` fit neither, was filed anyway, and was **closed without comment**. The other three XRPLF repositories have no templates. ⚠ **Re-check rather than inheriting that sentence.**

⚠ **FILING is governed by `docs/UPSTREAM-FILING-PROTOCOL.md`, ruled 2026-09-01, and `make check-filing` enforces the mechanical half.** Five rules: an adversarial review runs **BEFORE** filing and gates it; a prose word cap **the gate prints** with one concrete ask; **no positives-only filings to a bug tracker**; no negative claim without its recorded search; plain English and short sentences. ⚠ **The 2026-09-01 audit found every claim in the six open filings still standing at upstream HEAD — so the research was sound and the ORDER OF OPERATIONS was the defect.** A review that runs after submission cannot prevent anything; it can only produce a public correction.

Two rules that apply to capture:

- **Positive observations count**, but only when specific and non-obvious — a design decision that turns out to be better than it looks once you have read the source. Anything that could be said about any competent codebase is padding.
- **Nothing moves out of `Observed` in a coding session.** Promotion requires verification against source, a grade, and a citation, and sending is a Desktop-project decision. A coding session that files an upstream issue on its own initiative has skipped the review this project applies to everything else.
