## 0. EXECUTIVE SUMMARY & PRIORITY FOCUS EVALUATION

### (1) Adjudication Analysis (`docs/reviews/REVIEW-010c-...`)
* **Circularity of Leg A:** **AFFIRMED.** Leg A's construction in `docs/reviews/REVIEW-010a-gemini-r-and-rho-2026-08-18.md:189-204` includes `stmt_bytes` (the serialized Fiat-Shamir statement) in the KDF preimage for $r$. Because $stmt\_bytes$ contains $C_1 = r \cdot G$, $C_{2,i} = m \cdot G + r \cdot pk_i$, and $PC_m = m \cdot G + r \cdot H$, computing $stmt\_bytes$ requires $r$, creating an uncomputable circular dependency. Dismissal on this point was mathematically required, not an adjudicator bias.
* **Fabricated KAT Vectors:** **AFFIRMED.** Leg A's asserted intermediate values in §3.2 are demonstrably fabricated:
  * Leg A asserts an IKM length of 188 bytes, but the serialized length of its own defined fields is exactly 222 bytes ($10 + 19 + 36 + 84 + 37 + 36$).
  * Leg A claims in §3.1 that $aux = 0^{32} \implies \text{mask} = 0^{32}$, while its own §2.3 defines $\text{mask} = \text{SHA-256}(\text{tag\_hash} \parallel \text{tag\_hash} \parallel aux) \neq 0$.
  * The PRK, OKM, and derived $r$ values were hallucinated without executing HMAC-SHA-512.

### (2) Adopted Ruling & Test (`t-r-and-rho-construction.ts`)
* **Soundness & Uniqueness:** The core KDF construction is sound provided the CSPRNG is functional. However, the pre-signing detection rule (§7) introduces severe persistence and confidentiality failure modes.
* **False-Pass in Test:** **CONFIRMED.** Line 183 of `t-r-and-rho-construction.ts` checks collisions across `vectors.map((v) => v.expected)` rather than the computed `deriveScalar(v)` values, creating a false-pass mode for separation validation.

### (3) The Hedge Flip (`WCONF_HEDGE=1`)
* **Verification Gap:** **CONFIRMED & CRITICAL.** The restructured `nonce-crosscheck.ts` only asserts that the default binary produces non-identical proofs (`sigma(proofOurs) !== sigma(again)`). Because pristine upstream `mpt-crypto` also draws `RAND_bytes` and produces non-identical proofs, the default build has **zero verification** proving its nonces are generated by the patched KDF rather than upstream's unhedged RNG.

### (4) Architecture Document (`docs/architecture/ARCHITECTURE-2026-08-18.md`)
* **Contradictions & Open Questions:** §8 lists the persistence of $\rho$ as an unsettled open question that "did not affect the ruling." In Pedersen balance commitments ($B = b \cdot G + \rho \cdot H$), failing to persist $\rho_{out}$ makes subsequent spending mathematically impossible.
* **Build Sequence Contradiction:** §6 Step 3 mandates wiring end-to-end Sends and Converts *before* Gate 5 (ADR-0001 `Accepted`), directly violating §5's prohibition against building application logic.

### (5) ADR-0001 Edits
* **Premature Precondition Closure:** ADR-0001 line 267 marks Precondition 3 for §(a) as "met" based on an architectural policy ruling, before any confirmation UI or OS-level IPC has been designed or implemented.

### CRITICAL SEVERITY

#### [CRITICAL-01] Undecided $\rho$ Persistence Causes Permanent Loss of Funds
* **File & Line:** `docs/architecture/ARCHITECTURE-2026-08-18.md:122-124`, `docs/reviews/REVIEW-010-RULING-r-and-rho-2026-08-18.md:46-56`
* **Concrete Failing Scenario:**
  A holder executes a `ConfidentialMPTSend`. Under adopted Leg B, $\rho_{out}$ is derived from ephemeral `entropy64` and explicitly forbidden from being derived from $sk_A$ or the master seed. The transaction succeeds on Devnet. In the subsequent transaction, the zero-knowledge proof requires the witness $\rho_{in} = \rho_{out}$. Because ARCHITECTURE §8 treats $\rho$ persistence as an open question ("Whether rho must be persisted... Not adjudicated — it did not affect the ruling"), if the signer implementation does not store $\rho_{out}$, $\rho_{in}$ cannot be reconstructed. The holder's remaining balance is permanently locked and unspendable on-chain.
* **Concrete Fix:**
  Strike the open question from ARCHITECTURE §8. Formally rule that $\rho_{out}$ is a mandatory persistent state component. Define an atomic storage schema in the local signer requiring $(\text{account}, \text{issuance}, b_{new}, \rho_{out})$ to be durably committed before transaction dispatch.

#### [CRITICAL-02] Verification Gap: Default Hedged Binary Indistinguishable from Upstream RNG
* **File & Line:** `tools/spike-2026-08-18/nonce-crosscheck.ts:134-142`, `tools/spike-2026-08-18/build.sh:69-70`
* **Concrete Failing Scenario:**
  The default build configuration sets `WCONF_HEDGE=1`. In `nonce-crosscheck.ts`, the default binary (`mptool-patched`) is tested with:
  ```typescript
  check("DEFAULT build does NOT reproduce — it is hedged, as ruled", sigma(proofOurs) !== sigma(again));
  ```
  If a compiler flag error, link misconfiguration, or patch failure causes `mptool-patched` to bypass `wconf_generate_nonces` and execute upstream `mpt-crypto`'s pristine `RAND_bytes` loop, `sigma(proofOurs) !== sigma(again)` **STILL PASSES**. Upstream `mpt-crypto` also draws entropy and produces non-reproducing proofs. The test harness only verifies deterministic derivation on a non-default binary (`/tmp/wconf/mptool-deterministic`), leaving the production default binary with zero proof of correct nonce derivation.
* **Concrete Fix:**
  Add a test harness injection interface in the hedged build (e.g. `wconf_generate_nonces_test(..., aux_override)`) that allows `nonce-crosscheck.ts` to supply a fixed `aux` and verify byte-exact KAT outputs against the default hedged code path.

### HIGH SEVERITY

#### [HIGH-01] Pre-Sign Randomness Ledger Exposes Transaction Graph to Same-Host Adversaries
* **File & Line:** `docs/reviews/REVIEW-010-RULING-r-and-rho-2026-08-18.md:120-137`
* **Concrete Failing Scenario:**
  ADR-0001 §(a) and ARCHITECTURE §3 explicitly rule that a hostile same-host process is in the threat model. REVIEW-010 ruling §7 mandates recording $r\_commit = r \cdot G$ ($C_1$) in an unencrypted durable local file. A hostile same-host process reads the local ledger file and matches the recorded $C_1$ values against the public XRPL ledger. Because $C_1$ is broadcast in clear on every Send and $r$ is broadcast on Convert, the attacker correlates the holder's local identity with on-chain transactions, deanonymizing transaction timing, counterparties, and sequence numbers, as well as detecting aborted transactions that were never broadcast.
* **Concrete Fix:**
  Do not persist raw $C_1$ points on disk in plaintext. Store commitments as HMACs keyed under a local ephemeral session secret, or restrict the pre-sign duplicate cache to an encrypted lockbox with an aggressive rolling expiration and pruning policy.

#### [HIGH-02] False-Pass Separation Assertion in KAT Harness
* **File & Line:** `tools/spike-randomness-2026-08-18/t-r-and-rho-construction.ts:183-189`
* **Concrete Failing Scenario:**
  The structural separation check in `t-r-and-rho-construction.ts` executes:
  ```typescript
  const allOutputs = vectors.map((v) => v.expected);
  if (new Set(allOutputs).size !== allOutputs.length) { ... }
  ```
  This checks uniqueness over the hardcoded fixture strings (`v.expected`), not the outputs of `deriveScalar(v)`. If an implementation defect in `deriveScalar` causes multiple distinct vector inputs (e.g. varying `role` or `txType`) to produce identical scalars, this separation check will still output `MATCH separation: all vector outputs differ`, masking cross-domain collisions.
* **Concrete Fix:**
  Change line 183 to evaluate actual derived outputs:
  ```typescript
  const allOutputs = vectors.map((v) => deriveScalar(v));
  ```

#### [HIGH-03] Pre-Sign Ledger Deadlock on Unclean Process Termination
* **File & Line:** `docs/reviews/REVIEW-010-RULING-r-and-rho-2026-08-18.md:125-131`
* **Concrete Failing Scenario:**
  The signer derives $r$, registers $r\_commit$ as `pending` in the durable ledger, and begins proof computation. The process crashes or is killed by the OS (OOM/power loss) before emitting the signed transaction. Step 7 specifies that `pending` is cleared only on a "hard local failure before emission" during active execution. On reboot, the entry remains marked `pending` indefinitely. When the client retries the transaction under identical context parameters, the signer refuses to sign (`ERR_R_COLLISION_DETECTED`), permanently locking the transaction flow.
* **Concrete Fix:**
  Add a lease/timeout mechanism to `pending` records and implement an explicit crash-recovery cleanup protocol during signer initialization.
