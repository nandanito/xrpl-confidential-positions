Findings:
- [high] F-10 overclaims unreachability from a public-balance success path (CLAIMS.md:146)
  F-10 says the confidential balance is unreachable from every vault and lending transaction, but the GAP-8 lifecycle funds lender and borrower publicly and then runs the vault/lending operations against those public balances. The live confidential balance is on an unrelated holder and is only checked as untouched. That proves a confidential-capable issuance with a live confidential balance elsewhere does not reject the lifecycle; it does not prove each vault/lending transactor cannot reach, consume, mutate, or misreport a confidential balance on a relevant actor/holder when one exists. Impact: the A-grade restoration can be cited as execution evidence for a stronger interoperability finding than the scripts actually establish.
  Recommendation: Keep E-40 narrowly at non-rejection/acceptance if desired, but leave F-10 below Grade A or reword it to match the evidence. To upgrade F-10, add targeted cases where the acting borrower/lender/holder has live confidential state and assert pre/post confidential fields, decrypted balances, and ConfidentialOutstandingAmount for each applicable transaction, including negative controls that attempt to use value held only confidentially.
- [medium] GAP-8 success evidence is not self-validating or fully persisted (tools/spike-2026-08-17/gap8-loan-ops.ts:14-19)
  The new harness records or prints engine results but does not assert tesSUCCESS. In gap8-loan-ops, LoanPay, LoanManage, and LoanBrokerCoverClawback are submitted and only logged to stdout; their results are not saved, not linked by transaction hash, and not picked up by the committed audit script. The other GAP-8 scripts similarly continue after failures and save whatever engine string was returned. Impact: the repository cannot independently substantiate the CLAIMS.md statement that every one of the fifteen paths returned tesSUCCESS; a failed or unvalidated run could still leave prose claiming closure.
  Recommendation: Make the GAP-8 harness fail or mark the run invalid on any non-tes result, persist validated transaction hashes/meta TransactionResult for all 15 transaction types, and extend audit-evidence.ts or a committed evidence table so the Grade A claim is re-queryable rather than dependent on ephemeral console output.
- [low] F-16 attributes identical signing bytes to a condition the script never checks (tools/spike-2026-08-17/gap8-lending-lifecycle.ts:109-111)
  The LoanSet script signs both parties with the same local payload variable computed before CounterpartySignature is inserted. That demonstrates this construction was accepted, but it does not demonstrate the specific claim that CounterpartySignature being isSigningField:false is what makes encodeForSigning identical after the counterparty signature is present. The positive finding therefore generalizes beyond the check actually performed.
  Recommendation: Either narrow F-16 to say both signatures in this accepted transaction were produced over the same pre-CounterpartySignature bytes, or add an explicit assertion that encodeForSigning(tx) is unchanged after adding CounterpartySignature and cite the codec/server definition that marks the field non-signing.

Next steps:
- Do not restore F-10 to Grade A until the unreachability wording is narrowed or backed by actor-level confidential-balance tests.

### 2. Non-Rejection vs. Unreachability (F-10 / E-40 Objection)
- **The Defect:** F-10 claims that the confidential balance is *"unreachable from every vault and lending transaction"*. 
- **The Reality:** The test harness funded `lender` and `borrower` with **cleartext public MPT** (`Payment` with `Amount: { mpt_issuance_id, value }`). All 15 transactors were executed using public amounts on accounts that never configured `HolderEncryptionKey`.
- **Why this fails:** Executing 15 transactors with public amounts and observing `tesSUCCESS` proves **non-rejection of the token issuance flag** (`lsfMPTCanHoldConfidentialBalance`). It does **not** prove that confidential balances are unreachable. Observing that an unrelated third-party account's confidential balance (`holder A`, `ConfidentialOutstandingAmount: 571`) remained unchanged is a completely bogus negative control — of course Charlie's balance does not move when Alice and Bob exchange public tokens.
- **Verdict:** The Grade A restoration for F-10 is **unjustified grade inflation**. Reachability across 14 of the 15 transactors remains an unexecuted architectural inference (Grade B/C), not an observed execution fact.

---

### 3. Asset Under Test & Live Confidential Balance Integrity
- The issuance `state.issuanceId` did have `Flags: 224` (`lsfMPTCanHoldConfidentialBalance`) and carried an active confidential balance on-ledger held by `holder A` (`ConfidentialOutstandingAmount: 571`).
- **However:** The asset balances *actively touched* by the vault and lending transactions were 100% public MPT. Neither the lender nor the borrower ever held a confidential balance or initialized encryption keys. The live confidential balance existed on the issuance, but was completely bypassed by the harness execution.

---

### 4. F-16 Dual-Signature Flow Validation
- In `gap8-lending-lifecycle.ts:102-117`, `LoanSet` was executed with `tx.SigningPubKey = bkp.publicKey` (borrower), encoded via `encodeForSigning(tx)`, and signed by both borrower and lender (`lkp`).
- **Overstatement:** F-16 claims the flow works *"from the specification alone, with no undocumented prefix or field-ordering trick"*. In reality, the counterparty (lender) must sign a serialization that embeds the **borrower's** `SigningPubKey` in the top-level header, with the lender's public key placed inside `CounterpartySignature.SigningPubKey`. Calling this intuitive from the specification alone ignores that the counterparty is signing a payload carrying another party's public key header.

---

### 5. Generalisations & Grade Inflation
- **F-10 Regrading (B → A):** Grade inflation. 14 transactors were never executed against confidential balance fields.
- **Tautological Isolation Claims:** Presenting the fact that lender/borrower acquired no confidential fields as an empirical isolation finding, when neither account ever initialized encryption keys.

## Part 2: Findings by Severity

### CRITICAL

#### [CRITICAL-1] Grade Inflation and Unproven "Unreachability" in F-10 and U-24
- **Location:** `CLAIMS.md:146` (`F-10`), `UPSTREAM-FEEDBACK.md:109` (`U-24`), `docs/task-zero/XLS-66-INVESTIGATION-2026-08-16.md:322–326` (`GAP-8`)
- **What is Wrong:** F-10 asserts that the confidential balance is *"unreachable from every vault and lending transaction"* and restores Grade A on the basis that *"GAP-8 CLOSED 2026-08-17: all fifteen transactor paths executed"*. The diff states:
  > *"neither the lender nor the borrower ever acquired a single confidential field, and the confidential balance of an unrelated holder on the same issuance was untouched throughout — `ConfidentialOutstandingAmount` unchanged at 571 across the entire lifecycle"*
- **Why it Matters:** The test harness in `gap8-lending-lifecycle.ts` funded the lender and borrower exclusively with public MPT units (`Payment` with cleartext `Amount`). None of the 15 transactors were executed with confidential parameters, nor did they operate on accounts holding confidential balances. Observing that an unrelated third party's (`holder A`) confidential balance remained at 571 when lender and borrower performed public operations is a meaningless negative control. The run demonstrated **issuance non-rejection** (the issuance flag `Flags: 224` is accepted), not **confidential balance unreachability**. Restoring Grade A ("executed or cross-checked against two primary sources") for reachability across all 15 transactors is false.
- **What Would Falsify It:** An execution trace attempting to deposit, pay, or collateralize confidential balances in each of the 15 transactors and capturing explicit engine rejections or schema rejections.
- **Concrete Recommended Fix:** Downgrade F-10 to **Grade B**. Split the claim into two distinct statements:
  1. *Issuance Non-Rejection:* Vault and lending transactors accept an MPT issuance with `Flags: 224` (Grade A, executed).
  2. *Balance Unreachability:* Transactors operate only on public fields and cannot reach confidential balances (Grade B, inferred from schema and source reading, only `VaultDeposit` executed in GAP-9).

### HIGH

#### [HIGH-1] Silent Execution Drops and Missing Assertion Guards in Harness
- **Location:** `tools/spike-2026-08-17/gap8-lending-lifecycle.ts:119–144`, `tools/spike-2026-08-17/gap8-teardown.ts:5–10`
- **What is Wrong:** 
  1. In `gap8-lending-lifecycle.ts:119-128`, loan creation relies on an unverified 5-second delay (`await Bun.sleep(5000)`) followed by extracting `state.gap8LoanId`. If ledger closing takes longer or `createdNode` returns `undefined`, `LOAN` is undefined. Lines 130–144 guard `LoanPay` and `LoanManage` inside `if (LOAN)`. If `LOAN` is unset, `LoanPay` and `LoanManage` are **silently skipped** without throwing an error or failing the script.
  2. In `gap8-teardown.ts`, the `go()` helper records `r.engine` but contains zero assertions. If `LoanDelete` or `VaultDelete` returns `tecNO_ENTRY` or `tecNO_PERMISSION`, the script logs the engine code and continues tearing down dependent objects.
- **Why it Matters:** The research claim that *"every one returned tesSUCCESS"* rests on a harness that does not assert `tesSUCCESS` and allows transactor steps to silently no-op when asynchronous state extraction fails (which is why `gap8-loan-ops.ts` had to be created as a secondary script).
- **What Would Falsify It:** Adding strict assertions `if (engine !== "tesSUCCESS") throw new Error(...)` and verifying that the full unattended script completes.
- **Concrete Recommended Fix:** Replace conditional blocks and unasserted logging with explicit assertion guards:
  ```ts
  if (!r.engine.startsWith("tes")) {
    throw new Error(`Step ${label} failed with engine result: ${r.engine} (${r.message})`);
  }
  ```
  Poll `tx` status with a retry loop rather than a static `sleep(5000)`.

### MEDIUM

#### [MEDIUM-1] Overstated Dual-Signature Specification Claim in F-16
- **Location:** `CLAIMS.md:148` (`F-16`)
- **What is Wrong:** F-16 asserts:
  > *"The XLS-66 dual-signature flow works exactly as specified, first attempt... a two-party signing scheme that works from the specification alone, with no undocumented prefix or field-ordering trick, is not the norm"*
- **Why it Matters:** In `gap8-lending-lifecycle.ts:108-115`, `tx.SigningPubKey` is populated with the **borrower's** public key (`bkp.publicKey`). When `encodeForSigning(tx)` is generated, the counterparty (lender) signs a canonical payload that contains the borrower's public key in the top-level `SigningPubKey` field. If an integrator followed standard intuition and placed the lender's public key in `SigningPubKey` when generating the lender's signature, signature verification would fail. This is a subtle binary codec artifact, not an obvious property apparent "from the specification alone".
- **What Would Falsify It:** Demonstrating that counterparty signing requires specific knowledge of how `ripple-binary-codec` handles `SigningPubKey` vs `CounterpartySignature.SigningPubKey`.
- **Concrete Recommended Fix:** Moderate the praise in F-16 to document the requirement: note that the counterparty signs the canonical transaction payload embedding the primary account's `SigningPubKey`, while the counterparty's own public key is placed strictly inside `CounterpartySignature`.

#### [MEDIUM-2] Tautological Negative Control Presented as Protocol Isolation
- **Location:** `CLAIMS.md:146` (`F-10`), `docs/task-zero/XLS-66-INVESTIGATION-2026-08-16.md:326`, `tools/spike-2026-08-17/gap8-final-state.ts:6–9`
- **What is Wrong:** The text repeatedly cites as proof of composability isolation:
  > *"neither the lender nor the borrower ever acquired a single confidential field"*
- **Why it Matters:** The lender and borrower accounts were freshly funded faucet accounts that never registered encryption keys, never set `sfHolderEncryptionKey`, and only transacted in cleartext `sfMPTAmount`. It is structurally impossible for an account without encryption keys to acquire confidential ledger fields during standard vault/lending calls. Presenting the absence of confidential fields on these accounts as an experimental finding is presenting an unavoidable tautology as empirical evidence.
- **What Would Falsify It:** It is unfalsifiable by construction given the test setup.
- **Concrete Recommended Fix:** Remove the claim that lender/borrower not acquiring confidential fields proves protocol isolation, or explicitly state that these accounts never initialized confidential credentials.

#### [LOW-2] Fragile Fallback in Sequence Number Synchronization
- **Location:** `tools/spike-2026-08-17/gap8-lending-lifecycle.ts:24`
- **What is Wrong:** `freshSeq(a)` polls `account_info` up to 20 times waiting for validated sequence to match current sequence. On timeout, it falls back to `sequenceOf(a)`:
  ```ts
  async function freshSeq(a: string) { for (let i=0;i<20;i++){...} return sequenceOf(a); }
  ```
- **Why it Matters:** If the loop times out after 40 seconds, falling back to `sequenceOf(a)` directly triggers the faucet sequence race condition identified in `UPSTREAM-FEEDBACK.md` U-26 (`tefPAST_SEQ`).
- **What Would Falsify It:** Running on a lagging Devnet node where the loop exhausts 20 iterations.
- **Concrete Recommended Fix:** Throw an explicit error on timeout rather than falling back to an unvalidated sequence read.
