## Blocking

### R-1 — The domain recommendation in §9 reproduces the defect it diagnoses

**Problem.** §9 rejects the prompt's receivables design because `Convert`/`ConvertBack` publish drawdown amounts in plaintext, then proposes a fix — the vault converts the float once, every per-supplier event is a `ConfidentialMPTSend` — and concludes that "the public ledger shows nothing about which supplier drew how much."

That conclusion is too strong. XLS-0096 is explicit that sender and receiver identities are always public. Under the proposed structure an observer sees, for every drawdown: that the vault paid Supplier A, on what date, and at what frequency. Only the quantity is hidden.

**Why it matters.** The domain's stated justification is that drawdown behaviour reveals a supplier's cash position to competitors and to the buyer on the other side of the invoice. Drawdown *frequency and timing* carries much of that signal — a supplier moving from monthly to weekly draws is legible as cash stress without any amount being known. §9 asserts the commercial justification survives; it survives only in part, and the document does not say which part.

**Severity.** Blocking. This is the same class of error §9 accuses the original prompt of making, committed one paragraph later, in the document that recommends the domain.

**Fix.** Rewrite the §9 conclusion to state precisely what the structure buys: amounts hidden, counterparty graph and event timing public. Then answer the question that raises — is a facility whose drawdown *timing* is public still commercially viable, and is the residual leak acceptable to a real supplier? If the answer is no, the domain is weaker than claimed and the XLS-66 investigation becomes more urgent, not less. Either way the README must name the timing leak alongside the amount protection.

### R-2 — F-1 is graded above its evidence and framed as the wrong kind of finding

**Problem, part one — grading.** `CLAIMS.md` F-1 and TASK ZERO §8 D-1 assert that freshly-initialised balances, post-merge inboxes and clawed-back balances are publicly identifiable as exactly zero. The evidence is XLS-0096 §9.4's prose, the `EncZero` formula, and `mpt-crypto`'s README describing deterministic zero encryption. **The rippled transactors for `ConfidentialMPTMergeInbox` and `ConfidentialMPTClawback` were not read.** Whether the implementation actually writes the canonical value in all three cases is inference, not verification. The contradiction between spec and docs is Grade A; the consequence is Grade C and is written as though it were established.

**Problem, part two — framing.** §8 presents this as a privacy property being weaker than documented. XLS-0096 §9.4 presents public zero visibility as a deliberate benefit: it lets validators confirm a newly initialised balance contains no hidden value without the holder's key. So the defensible finding is narrower and duller: *the RippleX prerelease documentation states something the specification contradicts.* That is a documentation bug worth filing. It is not evidence that XLS-96 leaks more than its designers intended.

**Why it matters.** This is the flagship publication candidate. Published as framed, a RippleX engineer reads it and sees an author who mistook a documented design choice for a discovered weakness — which is exactly the "would find wrong" failure the publishing bar exists to prevent, and it would discredit the five sound findings alongside it.

**Severity.** Blocking for publication. Not blocking for the build.

**Fix.** Read `ConfidentialMPTMergeInbox` and `ConfidentialMPTClawback` in rippled 3.3.0 and settle what is actually written. Regrade. Restate the finding as documentation drift, and separate it cleanly from the observer-harness experiment, which remains worth running on its own merits.

### R-3 — ADR-0001 leaves XRPL account key custody undecided

**Problem.** The ADR correctly identifies that the ElGamal encryption key and the XRPL account signing key are distinct keys with distinct lifecycles, and decides custody for the first. It never decides custody for the second. The demo therefore has an unresolved custody question at the exact point the decision record claims to have resolved custody.

**Why it matters.** TASK ZERO item 4 says: *do not carry an unstated assumption past this point.* This is one. It also affects the README's central claim — "the server cannot move holder funds" is true for spending confidential balances, but a server holding a holder's XRPL account key can submit `ConfidentialMPTMergeInbox` (proof-free), can transact the holder's *public* MPT balance, and can act on the account generally. The claim as written is broader than the property.

**Severity.** Blocking. It is the specific failure mode the item was written to prevent.

**Fix.** Add section (d) to ADR-0001 deciding XRPL account key custody, and narrow the README claim to: the server cannot spend holder *confidential* balances, and state what it can do if it holds the account key.

### R-4 — The README describes a non-existent system in the present tense

**Problem.** "This application's server never receives holder key material and cannot move holder funds." "Holders generate and keep their own encryption keys, and produce their own proofs on their own machines." No application exists. These are design intentions written as operating properties.

**Why it matters.** The repository's premise is that capability claims must trace to a test result. The front page currently makes untested capability claims about software that has not been written. That is the P-5 category, on the page most likely to be read.

**Severity.** Blocking, and cheap to fix.

**Fix.** Head the trust-model section "Intended design — not yet implemented" and move every claim to the conditional until a test exists. Add a `CLAIMS.md` PENDING row for each.

## Non-blocking, fix before the next document

### R-5 — Date inconsistency across the whole set

Every document is dated 2026-08-12, inherited from the BLOCK 0 briefing's capture date. The research ran on 2026-08-13. In a project whose core discipline is date-stamping observations, the entire document set carries a date on which none of its observations were made. Rename `TASK-ZERO-2026-08-12.md`, correct the headers, and keep the briefing's own capture date distinct from the research date.

### R-6 — The fee mechanism is asserted, only the result is verified

E-5 states 100 drops and explains it as `10 × (1 + 9)` from `kConfidentialFeeMultiplier = 9`. The 100-drop figure is corroborated by the RippleX fee table, so the number is Grade A. The arithmetic is not: `Transactor::calculateBaseFee` was never read, so the relationship between the constant and the result is inferred. Read it, or drop the explanation and keep the number. A wrong mechanism attached to a right number is precisely what a spec author notices.

### R-7 — Metadata cap unexamined

§6 concludes transaction size is not a binding constraint on the basis of `kTxMaxSizeBytes = megabytes(1)`, and adds "and will not become one" — a prediction, not a finding. But `Protocol.h` also defines `kOversizeMetaDataCap = 5200`. A confidential transaction's metadata carries updated ledger objects containing ciphertexts for sender, receiver, issuer mirrors and optional auditor mirrors. Whether that approaches 5200 bytes was not checked. Check it, and delete the prediction.

### R-8 — GAP-4 was probably closable and was left open

GAP-4 rests on a source comment saying `sfDomainID` "will always be empty unless writing to it has been enabled by an amendment." Which amendment was not established. `PermissionedDEX` is `Supported::Yes` in 3.3.0 and is the likely candidate. Grepping `MPTokenIssuanceCreate` and `MPTokenIssuanceSet` for `sfDomainID` and its amendment guard is minutes of work and would probably resolve it without a devnet transaction. Presenting a closable question as a named gap is not the same integrity move as recording an unreachable source.

### R-9 — The local signer's provenance is an unnamed trust assumption

ADR-0001 concludes that holder-side proving means the operator cannot spend holder funds. If the issuer writes and distributes the signer binary, the holder is trusting the issuer's build. The property becomes "the operator cannot spend holder funds *provided the signer does what it claims*," and the ADR does not say so. Name it, and say what would discharge it — reproducible builds, source distribution, or an explicit statement that the demo does not attempt to solve it.

### R-10 — The project depends on a release-candidate library and does not say so

`mpt-crypto` is at `0.4.0-rc4` with 33 open issues and 18 open pull requests. Proof formats and byte lengths could change before 1.0, and every size in §3 and §6 is derived from the current formats. No risk item names this. It belongs in §11 alongside the other three.
