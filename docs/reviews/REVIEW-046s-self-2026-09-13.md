## Findings

### 1. HIGH — the issuer can erase the whole float, and no option or disclosure names it

`facility/run-facility.ts:323` creates the issuance with `tfMPTCanClawback`. rippled `3.3.0` `ConfidentialMPTClawback.cpp:72` requires the sender to be the issuer, `:80` requires `lsfMPTCanClawback`, and `doApply` at `:146-179` sets the holder's inbox and spending balances to the canonical encrypted zero and reduces both `ConfidentialOutstandingAmount` and `OutstandingAmount`. The proof is made with the issuer's ElGamal secret over the holder's `sfIssuerEncryptedBalance` (`:107-117`; `mpt_utility.h:299-305`).

So the bank's seed plus the issuer's ElGamal secret remove the Dedicated Account's entire confidential float in one transaction. That is a power over the float held by a **different** credential from the one the request is about. Options 1 to 5 do not touch it. Option 2's *"makes 'whoever holds that key can move the whole float' false"* is true of the Dedicated Account's key and leaves the float removable by the issuer's.

Whether that is a defect is a design question — the bank is issuer and funder, and clawback may be intended. But a custody request that does not name it prices the wrong set of credentials, and Option 1's disclosure would be incomplete without it.

### 2. HIGH — power 2 has a second holder, and Option 5's benefit is overstated because of it

Every `ConfidentialMPTSend` carries `IssuerEncryptedAmount` — the request's own citation, `xrpl.rs:1182` — and every `MPToken` carries `sfIssuerEncryptedBalance`. The issuer's ElGamal secret therefore reads every per-supplier amount and every balance (P-9), and issuer keys cannot be rotated (F-2, P-10). In this facility it is a standalone keypair (`run-facility.ts:346`) stored in `~/.wconf/facility-state.json` beside the seeds.

The request says *"one credential still reads every movement this account is an endpoint of"* and recommends a disclosure that *"one key reads the whole book and it cannot be rotated"*. Both are true of the Dedicated Account's key, and **a second key reads the whole book regardless**. Option 5 says *"A leak of one seed then reads that partition and no other"* — true of Dedicated Account seeds, but partitioning bounds nothing about the issuer's secret, which reads every partition. The recommendation calls power 2 *"the larger of the two exposures"*; no option narrows the issuer's copy of it.

### 3. MEDIUM — the decryption credential is a required input to every confidential movement, which changes Option 2's shape and cost

`mpt_get_confidential_send_proof` takes *"the sender's 32-byte private key"* and proves *"balance ownership"* (`mpt_utility.h:233-269`); `mpt_get_convert_back_proof`'s witness is *"(b, rho, priv)"* (`:272-291`). The signer passes `inputs.sk` to `send_proof` (`signer/src/prover.rs:724-733`). A drawdown or a retirement from the Dedicated Account cannot be built without its ElGamal secret.

The request treats movement and decryption as two separable powers. They are not independent: decryption is a necessary part of movement, for the confidential balance. Three consequences it does not state:

- **Option 2 splits more than it says.** Under a signer list with the master disabled, a quorum cannot move the confidential float without whoever holds the ElGamal secret. *"One operator holding every signer key still moves the whole float alone"* needs *"and the ElGamal secret"*.
- **Availability is an unpriced cost.** The ElGamal secret must be on hand for every drawdown and retirement, so it cannot be cold-stored. Under 2a that secret is derived from the disabled master seed, so disabling the master does not let the seed go offline.
- **Losing the ElGamal secret strands the confidential float.** No proof means no Send and no ConvertBack. The only thing left that acts on it is the issuer's clawback, which removes the float rather than recovering it — finding 1 again.

The public balance, after a ConvertBack, moves by signature alone; this is scoped to the confidential balance.

### 4. MEDIUM — *"under `0600`"* is false for the Dedicated Account's seed

§ What is and is not at stake says *"the seeds are in `/tmp/wconf/state.json` and `~/.wconf/state.json` under `0600`"*. The Dedicated Account's seed is not in either file. It is `.dedicated.seed` in `~/.wconf/facility-state.json`, **mode `0644`**, beside the bank's seed, three supplier seeds and the issuer's ElGamal secret. Measured by `stat` on 2026-09-13.

`facility/run-facility.ts:106-107` creates the directory and writes the file with no mode argument, so they take the process umask (`022` here). The directory is `0700` today only because a **different script**, `tools/rebuild-env.sh:159`, runs `chmod 700` on it. On a machine where the facility runs before that script, the directory is `0755` and every seed in the file is readable by other local users.

A second site, read at source and not executed: `facility/src/signer.ts:113-116` writes the seed into `profile.json` with no mode, in a directory made with no mode. The signer later sets that directory to `0700` when it binds its socket (`signer/src/ipc.rs:105`), for the socket's sake, and never checks the profile's own mode. Between the write and the bind, the profile sits in a directory other users can traverse.

The request's conclusion — Devnet MPT has no value, so this is not a live incident — survives. The sentence supporting it does not, and it is a security sentence in the document about who can reach this seed.
