### 1. ⚠ Is E-171 CORRECT? Re-derive it yourself; do not accept our account.

**E-171 IS FALSE (INCORRECT).** The correction published against B-19 is itself a false finding based on a flawed feature-resolution assumption.

#### Re-derivation from `ed25519-dalek 2.2.0`'s `Cargo.toml`:
1. In `ed25519-dalek 2.2.0` `Cargo.toml`:
   ```toml
   [features]
   alloc = [
       "curve25519-dalek/alloc",
       "ed25519/alloc",
       "serde?/alloc",
       "zeroize/alloc",
   ]
   std = [
       "alloc",
       "ed25519/std",
       "serde?/std",
       "sha2/std",
   ]
   zeroize = [
       "dep:zeroize",
       "curve25519-dalek/zeroize",
   ]
   ```
2. In `ed25519-dalek`, `zeroize` is an optional dependency (`optional = true`), and the feature `zeroize` is explicitly defined using Cargo's namespaced syntax (`dep:zeroize`). Under Cargo's RFC 3143 rules (standard in Edition 2021):
   - When `dep:zeroize` is used in `[features]`, Cargo **does not** create an implicit `zeroize` feature for the optional dependency.
   - When `alloc` specifies `"zeroize/alloc"`, it enables the `zeroize` crate dependency and activates its `alloc` feature.
   - **Crucially**, enabling `"zeroize/alloc"` does **NOT** activate `ed25519-dalek`'s own `zeroize` feature, nor does it activate `"curve25519-dalek/zeroize"`.
3. When `ed25519-dalek` was configured with `default-features = false, features = ["std"]`:
   - Cargo passes `--cfg feature="std"` and `--cfg feature="alloc"` to `rustc`.
   - Cargo does **NOT** pass `--cfg feature="zeroize"`.
4. In `ed25519-dalek 2.2.0/src/hazmat.rs`:
   ```rust
   #[cfg(feature = "zeroize")]
   use zeroize::{Zeroize, ZeroizeOnDrop};

   #[cfg(feature = "zeroize")]
   impl Drop for ExpandedSecretKey {
       fn drop(&mut self) {
           self.scalar.zeroize();
           self.hash_prefix.zeroize()
       }
   }

   #[cfg(feature = "zeroize")]
   impl ZeroizeOnDrop for ExpandedSecretKey {}
   ```
   Because `--cfg feature="zeroize"` is not set, `#[cfg(feature = "zeroize")]` evaluates to **`false`**. `ExpandedSecretKey` and `SigningKey` **did not** implement `Drop` or `ZeroizeOnDrop`.
5. Furthermore, `alloc` only enables `"curve25519-dalek/alloc"`, NOT `"curve25519-dalek/zeroize"`. `Scalar::zeroize()` in `curve25519-dalek` was also uncompiled.

**Conclusion:** B-19's original premise was **true**: `zeroize` was indeed OFF for those nine days. E-171 confused the presence of the `zeroize` crate in the build graph with the activation of `ed25519-dalek`'s `zeroize` feature gate.

### 2. Does B-21 change the signing construction in any way?

**No.** The cryptographic and mathematical constructions for both algorithms are byte-for-byte identical:
- **Secp256k1:** `AccountKey::sign_with_aux` still hashes `message` via `sha512half`, feeds `OneShotAux` (now holding `Zeroizing<[u8; 32]>`) to `sign_prehash_with_rng`, normalizes `S`, and encodes as DER. `OneShotAux::fill_bytes` yields the exact same byte stream.
- **Ed25519:** `sha512_zeroizing(&[k.as_bytes()])` evaluates plain `Sha512` over `k.as_bytes()`, producing the exact same 64-byte expanded key. `sha512_zeroizing(&[ED25519_NONCE_HEDGE_DST, &aux[..]])` evaluates plain `Sha512` over `DST || aux` in identical order, producing the exact same mask XORed into `hash_prefix`.
- **`fresh_aux`:** Still reads 32 bytes from `store::getrandom` into a 32-byte array and branches identically on `Ok` (`Some`) vs `Err` (`None`).

Only container types (`Zeroizing`), explicit slice wiping (`digest.as_mut_slice().zeroize()`), and `Drop` behaviors changed.

### 3. Can `check-zeroize-bounds.py` false-pass, and in which direction?

**Yes, in the false-positive direction (certifying a safety property that does not hold).**

2. **`(type)` vs `(bound)` in Mutation Testing:**
   - Testing a `T: ZeroizeOnDrop` compile-time bound establishes only that `Drop` will be invoked by `rustc` when the binding falls out of scope.
   - It does **not** prove:
     - That dead stack copies from Rust moves were wiped (Rust moves are bitwise `memcpy` that do not zero the source).
     - That compiler optimizations did not spill registers or elide stores.
     - That internal hasher states (`Sha512` block buffer) were wiped.
3. **Unrelated Mutation Compilation Failures:**
   - If a mutation script replaces `Zeroizing<[u8; 32]>` with a syntax error or an unresolvable type, any compiler error satisfies a naive nonzero-exit check, false-passing the mutation test without testing the trait bound.

### 4. Are the two new tests real falsifiers, or one layer away from what they are named for?

#### `the_signing_helpers_secret_locals_wipe_on_drop`: **ONE LAYER AWAY.**
- **The Defect:** The test is named `the_signing_helpers_secret_locals_wipe_on_drop`, but it **does not test the signing helper (`AccountKey::sign_with_aux`)**.
- It directly calls `sha512_zeroizing(&[b"probe"])`, `fresh_aux()`, and constructs `OneShotAux::new(...)`.
- If `AccountKey::sign_with_aux` were modified to revert to un-zeroized `Sha512::digest` or plain arrays for `h`, `mask`, or `aux`, **this test would remain completely green**. It tests isolated helper functions, not the signing helper's locals.

#### `the_wiping_hash_is_sha512_over_its_parts_in_order`: **REAL FALSIFIER FOR `sha512_zeroizing`, BUT ONE LAYER AWAY FROM `sign_with_aux`.**
- For `sha512_zeroizing` itself, it is a real unit falsifier: it asserts standard SHA-512 digest equivalence, multi-part concatenation, and order-sensitivity.
- However, it does not falsify whether `sign_with_aux` feeds the DST and `aux` in the correct order (though external KATs cover that).

### 7. What secret material in the signing path is STILL unwiped that B-21 should have covered?

1. **`sha512half` in Key Derivation (`AccountKey::ed25519_from_entropy` & `from_entropy`):**
   - **Verdict on scope:** Leaving `sha512half` out of scope was **the wrong call**. In `ed25519_from_entropy`, `sha512half(entropy)` computes `Sha512::digest(entropy)`. The 64-byte `full` digest and the returned `[u8; 32]` holding root private key material are left completely unwiped on the stack. Wiping ephemeral nonce entropy while leaving long-term root seed derivation buffers unwiped in the same module is an arbitrary and inconsistent boundary.
2. **`OneShotAux` Integer Conversion Temporaries (`signer/src/xrpl.rs:463-472`):**
   - In `next_u32` and `next_u64`, stack buffers `let mut b = [0u8; 4]` and `let mut b = [0u8; 8]` copy secret auxiliary entropy from `self.bytes` and are left unwiped when returning integers.
3. **`AccountKey` Struct Itself:**
   - `AccountKey` and `Inner` do not implement `Drop` or `ZeroizeOnDrop`. If an `AccountKey` is moved or dropped, the outer struct leaves its secret fields unwiped.
4. **Seed Decoding (`decode_ed25519_seed`, `decode_family_seed`):**
   - Return raw `[u8; 16]` arrays of decoded secret entropy with no zeroization on drop.

### 8. Is removing the `zeroize` dev-dependency correct?

**Yes.**
- In Cargo, all dependencies declared under `[dependencies]` are automatically available to integration tests in `tests/*.rs`.
- `zeroize = { version = "1", default-features = false }` in `[dependencies]` provides `Zeroize` and `ZeroizeOnDrop` (which reside in `core` without requiring `alloc`).
- Removing the redundant `[dev-dependencies]` entry eliminates duplicate declarations with no compilation breakage or feature degradation.
