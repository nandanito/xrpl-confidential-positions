## Leg A — Codex (full repository access)

# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

No ship: the EncZero reimplementation diverges from upstream on the only rejection-sampling branch, and the key-file error path still leaks secret-adjacent path data.

Findings:
- [high] EncZero rejection sampling does not mirror upstream after an invalid scalar (tools/observer-harness.ts:67-68)
  The first hash path matches the documented 51-byte layout, and zero/out-of-range scalars are rejected. The problem is the retry path: this code rehashes only the 32-byte digest (`r = sha256(r)`), while upstream `generate_canonical_encrypted_zero` copies the 32-byte digest into the first 32 bytes of the 51-byte buffer and hashes all 51 bytes again. That branch is rare for secp256k1, but this is consensus-relevant deterministic encoding; if any public input lands on an invalid first scalar, this harness will compute a different EncZero than validators and can falsely fail F-1. The live-ledger positive check and perturbed-account control do not exercise this branch, so E-59 overstates the cross-check coverage.
  Recommendation: Mirror upstream exactly by keeping a 51-byte hash buffer for retries, copying the invalid digest into bytes 0..31, leaving bytes 32..50 as upstream does, and hashing 51 bytes each iteration. Add a unit test that forces the first digest invalid by stubbing the hash/scalar check so the retry branch is covered.
- [medium] Missing or unreadable key files leak the key-file path through uncaught fs errors (tools/issuer-decrypt-balance.ts:51-60)
  `readFileSync(args[i + 1], "utf8")` is outside a try/catch. If `--key-file` is missing, mistyped, unreadable, or points at a path the process cannot access, Bun/Node will print an uncaught exception that includes the path. That violates the stated requirement that the key-file path is not logged and creates avoidable leakage around secret storage layout.
  Recommendation: Validate that `--key-file` has a non-flag value, catch filesystem errors, and emit a generic message such as `could not read key file` without including the path or raw exception text.
- [medium] Issuer CLI can silently treat unknown flag values as positional accounts (tools/issuer-decrypt-balance.ts:65-68)
  The positional parser removes values for only three known flags and never rejects unknown flags. With a typo or future flag like `--keyfile ./issuer.sk <account> <id>` while `WCONF_ELGAMAL_SK` is set, `./issuer.sk` becomes `account` and the real account becomes `issuanceId`; with an unknown flag whose value is a valid account, the tool can query and report on the wrong holder. For a research evidence command, silent argument reinterpretation can produce false evidence rather than a clean usage failure.
  Recommendation: Replace the filter-based parser with explicit token consumption: reject unknown flags, require values for valued flags, reject extra positionals, and validate account/issuance shapes before making ledger RPCs.

Next steps:
- Fix the EncZero retry branch before relying on E-59 as evidence.
- Harden issuer-view argument and key-file error handling, then rerun the stated negative controls.

## Leg B — Gemini (diff only, no file access)

# Adversarial Code & Research Review

## Priority Focus Assessment

### 1. Reimplementation of `canonicalEncZero` in `observer-harness.ts`
- **Buffer layout (51 bytes)**: Exact match for `7 ("EncZero") + 20 (AccountID) + 24 (MPTokenIssuanceID)`. Offsets `0`, `7`, and `27` are correct.
- **Rejection sampling & termination**: `isValidScalar` strictly enforces $0 < n < \text{CURVE.n}$. With secp256k1 order $n \approx 2^{256} - 2^{128}$, rejection probability is $\approx 2^{-128}$, ensuring termination in 1 iteration with overwhelming probability.
- **Scalar parsing**: `BigInt("0x" + hex(r))` correctly handles leading zero bytes as big-endian integers in JavaScript.
- **Compressed encoding**: `@noble/curves` `Point.prototype.toRawBytes(true)` outputs standard 33-byte SEC1 compressed points ($0x02/0x03$ prefix + $X$-coord). Concatenating $C_1$ and $C_2$ produces the exact 66-byte (132 hex characters) ElGamal ciphertext expected on-chain for $m = 0$ ($C_1 = rG, C_2 = rQ$).
- **Defects identified**: Undeclared package dependency on `ripple-address-codec` prevents execution ([Finding 1](#finding-1-high---toolsobserver-harnessts38-packagejson12-18)); missing length check on `issuanceIdHex` can throw unhandled `RangeError` ([Finding 7](#finding-7-low---toolsobserver-harnessts60-65)).

### 2. `--assert-encrypted-zero` Assertion Soundness
- **Trivial pass risk**: Cannot pass trivially. Matching an on-chain 66-byte ciphertext requires exact byte equality with live ledger state ($2^{-528}$ random match probability). The negative control (`perturbedAccount`) verifies that flipping a bit in the AccountID produces a distinct ciphertext that collides with none of the account's ciphertext fields.
- **False failure risk**: A user passing a lowercase `MPTokenIssuanceID` on the CLI causes the object lookup to fail before assertion evaluation due to case-sensitive matching against rippled's uppercase response ([Finding 2](#finding-2-high---toolsobserver-harnessts128-toolsissuer-decrypt-balancets87)).

### 3. Secret Key Handling & Parsing in `issuer-decrypt-balance.ts`
- **Key isolation**: Secret keys are accepted only via `WCONF_ELGAMAL_SK` environment variable or `--key-file <path>`. There is no `--key` CLI argument, protecting against `ps` inspection and shell history logging.
- **Error path leakage**: Validation errors report only `key.length`; decryption failure errors output generic diagnostic text without echoing secret key material.
- **Parser defects**: Trailing `--key-file` without an argument causes an unhandled `TypeError` ([Finding 4](#finding-4-medium---toolsissuer-decrypt-balancets52-93)); unknown CLI flags corrupt positional argument resolution, and `--flag=value` syntax is silently ignored ([Finding 5](#finding-5-medium---toolsissuer-decrypt-balancets65-68)).

### 4. Confidentiality Claims & Prohibitions
- Output strings in both tools strictly adhere to confidentiality boundaries: amounts are reported as confidential, while transaction metadata (types, timestamps, counterparties, destination tags) and aggregate issuance confidential supply are explicitly marked public. Both tools prominently log that balances are never hidden from the issuer (and auditor, where configured).
- **Defect identified**: Documentation and header docstrings overclaim that `observer-harness.ts` "links no cryptography library" despite importing `@noble/curves` and `@noble/hashes` ([Finding 3](#finding-3-medium---claimsmd105-toolsobserver-harnessts11-13)).

### 5. Claims E-59 and Upstream Feedback U-34
- **CLAIMS.md E-59**: Claims harness self-verification and awards grade `A`. Because `observer-harness.ts` depends on an unlisted package (`ripple-address-codec`), it fails in clean environments, making Grade `A` unsupported by reproducible evidence ([Finding 1](#finding-1-high---toolsobserver-harnessts38-packagejson12-18), [Finding 3](#finding-3-medium---claimsmd105-toolsobserver-harnessts11-13)).
- **UPSTREAM-FEEDBACK.md U-34**: Fairly presents the upstream trade-offs by explicitly noting that upstream packages were curated for proof generation rather than external observers. However, it erroneously classifies `EncZero` derivation as a "constant" rather than a deterministic computation ([Finding 6](#finding-6-low---upstream-feedbackmd122)).

### HIGH

#### <a id="finding-1-high---toolsobserver-harnessts38-packagejson12-18"></a>Finding 1 (HIGH) - `tools/observer-harness.ts:38`, `package.json:12-18`
**Undeclared runtime dependency `ripple-address-codec` crashes harness on clean install**
- **What is wrong**: `tools/observer-harness.ts` imports `decodeAccountID` and `encodeAccountID` directly:
  ```typescript
  // tools/observer-harness.ts:38
  import { decodeAccountID, encodeAccountID } from "ripple-address-codec";
  ```
  Neither `package.json` nor `bun.lock` declares `ripple-address-codec`. In a clean checkout or CI environment, running `bun run tools/observer-harness.ts` throws `Cannot find package 'ripple-address-codec'`. This directly invalidates the claim in `CLAIMS.md` E-59 that the harness executes and self-verifies.
- **Why it matters**: The observer harness cannot execute in reproducible environments, breaking automated verification.
- **Recommended fix**: Add `"ripple-address-codec": "^5.0.0"` (or repository pinned version) to `package.json` dependencies and regenerate `bun.lock`.

#### <a id="finding-2-high---toolsobserver-harnessts128-toolsissuer-decrypt-balancets87"></a>Finding 2 (HIGH) - `tools/observer-harness.ts:128`, `tools/issuer-decrypt-balance.ts:87`
**Case-sensitive comparison on `MPTokenIssuanceID` fails valid queries with lowercase hex inputs**
- **What is wrong**: Both tools look up the target token using exact case-sensitive string matching:
  ```typescript
  // tools/observer-harness.ts:128 & tools/issuer-decrypt-balance.ts:87
  const mpt = (objs.result?.account_objects ?? []).find((o: any) => o.MPTokenIssuanceID === issuanceId);
  ```
  Rippled JSON-RPC returns `MPTokenIssuanceID` in uppercase hex (e.g. `00453A7D...`). When a user supplies standard lowercase hex on the CLI, `find` returns `undefined`, and both tools prematurely exit with error (`<account> holds no MPToken for <issuanceId>`).
- **Why it matters**: Valid queries and assertions fail on format convention differences rather than state mismatch.
- **Recommended fix**: Normalize both sides of the comparison to uppercase:
  ```typescript
  const mpt = (objs.result?.account_objects ?? []).find(
    (o: any) => String(o.MPTokenIssuanceID).toUpperCase() === issuanceId.toUpperCase()
  );
  ```

### MEDIUM

#### <a id="finding-3-medium---claimsmd105-toolsobserver-harnessts11-13"></a>Finding 3 (MEDIUM) - `CLAIMS.md:105`, `tools/observer-harness.ts:11-13`
**False claim that `observer-harness.ts` "links no cryptography library"**
- **What is wrong**: `CLAIMS.md` row E-59 and `observer-harness.ts` docstrings state:
  ```markdown
  <!-- CLAIMS.md:105 -->
  `tools/observer-harness.ts` holds **no keys and links no cryptography library** — it recomputes the canonical `EncZero` from three public inputs using only SHA-256 and secp256k1...
  ```
  ```typescript
  // tools/observer-harness.ts:11-13
  * ## It holds no keys, and it links no cryptography library
  * That is the point. An observer has neither.
  ```
  The implementation imports `@noble/curves/secp256k1` and `@noble/hashes/sha256`. Both are external cryptographic libraries. While the author intended to state that the harness does not link the vendored `mpt-crypto` C/WASM library, stating it "links no cryptography library" is factually false and overclaims purity.
- **Why it matters**: Research documentation must accurately describe component dependencies.
- **Recommended fix**: Update `CLAIMS.md:E-59` and `observer-harness.ts` to clarify:
  `"...holds no keys and links no upstream mpt-crypto C/WASM library, relying entirely on standalone pure-TypeScript primitives (@noble/curves and @noble/hashes)..."`

#### <a id="finding-4-medium---toolsissuer-decrypt-balancets52-93"></a>Finding 4 (MEDIUM) - `tools/issuer-decrypt-balance.ts:52, 93`
**Unhandled exceptions on missing `--key-file` argument and non-numeric `--max`**
- **What is wrong**: In `tools/issuer-decrypt-balance.ts`:
  1. Line 52 accesses `args[i + 1]` without bounds validation:
     ```typescript
     const raw = i >= 0 ? readFileSync(args[i + 1], "utf8") : process.env.WCONF_ELGAMAL_SK;
     ```
     If `--key-file` is passed as the final argument, `args[i + 1]` is `undefined`, causing `readFileSync` to throw an unhandled `TypeError` instead of exiting with status 2.
  2. Line 93 passes user input directly to `BigInt`:
     ```typescript
     const max = BigInt(flagValue("--max") ?? iss?.ConfidentialOutstandingAmount ?? "1000000");
     ```
     If `--max invalid` is passed, `BigInt("invalid")` throws an unhandled `SyntaxError`.
- **Why it matters**: CLI tools should handle argument errors gracefully with standard exit codes and diagnostic messages.
- **Recommended fix**: Validate `args[i + 1]` before calling `readFileSync` and wrap `BigInt` parsing in input validation.

#### <a id="finding-5-medium---toolsissuer-decrypt-balancets65-68"></a>Finding 5 (MEDIUM) - `tools/issuer-decrypt-balance.ts:65-68`
**Fragile positional argument parser misinterprets unrecognized flags and ignores `--flag=value` syntax**
- **What is wrong**: The positional argument filter only strips arguments immediately following three hardcoded flags:
  ```typescript
  const positional = args.filter((a, i) => !a.startsWith("--") && !(i > 0 && ["--key-file", "--max", "--field"].includes(args[i - 1])));
  ```
  - If any unrecognized flag with a value is supplied (e.g. `--endpoint wss://...`), the value is treated as a positional argument, corrupting `account` and `issuanceId`.
  - If flags are passed using `--field=AuditorEncryptedBalance` or `--max=5000`, `flagValue` returns `undefined`, silently reverting to default settings.
- **Why it matters**: Unrecognized or differently formatted CLI options silently corrupt parameters and execution targets.
- **Recommended fix**: Use a standard token parser or handle `--name=value` splitting and strict positional parsing.

**Mischaracterizes `EncZero` derivation as a "constant"**
- **What is wrong**: Row U-34 states:

  `EncZero` is an account- and issuance-specific deterministic ElGamal ciphertext computed from public inputs via hash-to-scalar rejection sampling and elliptic curve point multiplication. It is a canonical derivation function, not a constant.
- **Why it matters**: Inaccurate cryptographic terminology in upstream feedback weakens technical precision.

#### <a id="finding-7-low---toolsobserver-harnessts60-65"></a>Finding 7 (LOW) - `tools/observer-harness.ts:60-65`
**Missing input length check for `issuanceIdHex` in `canonicalEncZero`**
- **What is wrong**: `canonicalEncZero` allocates a fixed 51-byte buffer:
  ```typescript
  const input = new Uint8Array(51);
  input.set(new TextEncoder().encode("EncZero"), 0);
  input.set(decodeAccountID(account), 7);
  input.set(unhex(issuanceIdHex), 27);
  ```
  If `issuanceIdHex` contains more than 48 hex characters (24 bytes), `input.set` throws `RangeError: offset is out of bounds`. If fewer, remaining buffer bytes remain zeroed without validation.
- **Why it matters**: Malformed CLI arguments trigger an internal range exception rather than a clear validation error.
- **Recommended fix**: Assert `unhex(issuanceIdHex).length === 24` before inserting into `input`.

## Recording notes — not adjudication

1. **Codex leg A, the HIGH finding on rejection sampling, is a FALSE POSITIVE — verified against upstream source before this record was committed.** It claims the retry path must copy the invalid digest back into the 51-byte buffer and re-hash all 51 bytes. Upstream does not do that: `src/elgamal.c` calls `EVP_Digest(deterministic_scalar, kMPT_HALF_SHA_SIZE, …)` with `kMPT_HALF_SHA_SIZE == 32` (`include/mpt_protocol.h:18`), and its own comment reads *"chain-hash the 32-byte previous output"*. `r = sha256(r)` matches upstream exactly. **Following the recommendation would have introduced the divergence it warns about.** Its secondary point stands and is accepted: the retry branch is untested, and E-59 should not imply the live cross-check covers it.
2. **The two legs disagree about almost everything else, and both are useful.** Codex went at key handling and argument parsing; Gemini went at dependency hygiene, input canonicalisation and claim wording. Only the argument-parser defect was reached by both.
3. **Gemini leg B HIGH-1 is the most consequential: `ripple-address-codec` is imported but was never added to `package.json`.** It currently resolves only as a transitive dependency of `ripple-keypairs`. If that is right the tool breaks on a clean install, and E-59 Grade A rests on reproducibility.
4. **Gemini leg B MEDIUM-3 is plainly right about the wording.** The header says the tool "links no cryptography library" while importing `@noble/curves` and `@noble/hashes`. The intended meaning was "no XLS-96-specific or vendored library", and the sentence does not say that. The same wording appears in CLAIMS.md E-59.
5. Nothing here has been fixed. Adjudication follows.
