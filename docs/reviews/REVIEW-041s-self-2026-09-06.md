## S2-1 — HIGH, LIVE, and it inverts an assumption both tools were built on.

⚠⚠ **IN A GFM TABLE, A PIPE INSIDE A CODE SPAN IS A CELL DELIMITER. Only `\|` is
content.** The GFM spec says a pipe must be escaped to appear in a cell
*"including inside other inline spans"*. **Measured with `marked@18`:**

```
| E-1 | `a|b|c` | ev | A |     ->  cells: ["E-1", "`a", "b", "c`"]
| E-1 | a \| b  | ev | A |     ->  cells: ["E-1", "a | b", "ev", "A"]
```

⚠ **`stripCode()` protects code-span pipes, so `check-table-integrity` has been
BLIND to exactly the defect it exists to catch** — and its founding comment
argues for that protection explicitly: *"a naive `count('|')` flags every one of
them and the gate becomes noise."* **That rationale is false.** Those rows are
not noise; they are broken.

**FIVE live rows in `CLAIMS.md` render with more cells than their header, and
GFM discards the excess** — so the Grade column displays the wrong content:

| row | GFM cells | header | what the Grade column actually shows |
|---|---|---|---|
| E-48 | 8 | 4 | (grade text, truncated) |
| E-162 | 11 | 4 | **`Finding`** |
| E-214 | 6 | 4 | **a fragment of code** |
| E-222 | 6 | 4 | **`sort -u`** |
| **E-246** | 8 | 4 | (wrong) |

⚠⚠ **`E-246` IS THE ROW I WROTE THIS SESSION TO RECORD ROUND ONE.** The register
entry documenting a rendering defect is itself a rendering defect. **Fourth
distinct way this gate has certified a file whose rows do not render:** a blank
line (E-243), prose and `---` (E-244), a header/delimiter mismatch (REVIEW-040
H1), and now a code-span pipe.

**Falsified if:** a conforming GFM renderer treats an unescaped pipe inside a
code span in a table row as content.

## S2-2 — HIGH. My round-two fix moved `splitCells` AWAY from GFM.

Round two added code-span awareness to `splitCells` so the generators would stop
truncating claim cells. ⚠ **That was the wrong direction**: GFM does not protect
those pipes, so the generators now disagree with the renderer in the opposite
way. The end state that makes both correct is **escaping the pipes in the
source**, after which the two readings coincide.

⚠ **The seven "mis-split" rows reported in `E-246` were real, but the diagnosis
was inverted**: the naive `split("|")` agreed with GFM and the code-span-aware
version does not. **What was actually wrong is the SOURCE.**
