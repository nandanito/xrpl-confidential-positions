===== PROTOCOL.md =====
# Upstream filing protocol

**Ruled by the project owner 2026-09-01, after auditing the 2026-08-26 round.**

This binds every filing to an XRPLF repository. `make check-filing` enforces the
mechanical parts; the rest is judgement and is listed so it can be checked by a
person.

---

## Why this exists

Seven items were filed on 2026-08-26. An adversarial review run **after
submission** found **13 defects**, six graded *would embarrass*. Four of five
first-round issues needed same-day corrections in public.

The 2026-09-01 audit re-verified all six open filings at upstream HEAD: **every
claim still stands and none is stale.** So the content was recoverable. What was
not recoverable is the impression left by correcting four public issues within
hours of opening them.

⚠ **The defect was the order of operations, not the research.** Everything below
follows from that.

---

## The two commands

- **`/upstream-issue`** — drafts a filing from a verified finding.
- **`/issue-review`** — attacks the draft before it is sent. **Rule 1 gates on it.**

⚠ Both are slash commands in `.claude/commands/`, matching this project's three
existing ones — **user-invoked, never model-invoked**, because filing needs
authorisation every time.

⚠ **Both read the target repository's issue template first**, and that outranks
anything here. **Measured 2026-09-01:** `XRPLF/rippled` sets
`blank_issues_enabled: false` and offers only `bug_report.md` and
`feature_request.md`; `XRPL-Standards`, `xrpl-dev-portal` and `mpt-crypto` have
none. ⚠⚠ **`rippled#8118` fit neither rippled template, was filed anyway, and
was closed without comment.** Reading the template first would have stopped that
filing before it was written — which makes it the cheapest rule here and the one
that was missing.

---

## The five rules

### 1. Adversarial review runs BEFORE filing, and it gates

No filing is sent until an independent adversarial pass has run against the
**draft text and the frozen primary sources**, and every finding is resolved.

⚠ **A review that runs after submission cannot prevent anything.** It can only
produce a correction, and a correction is a public record that the filing was
not ready.

**The reviewer is given the draft and the sources, not the conclusion.**

### 2. A filing is at most 300 words, with one concrete ask

Counted over the issue body, excluding code blocks, quoted source and the
disclosure footer.

⚠ **`WORD_LIMIT` in `tools/check-filing.ts` is what enforces this, and the gate
prints the number it used.** This heading states the rule; that constant is the
instrument. If the two ever disagree, the gate is right and this line is the
defect — and neither the skills nor a draft may restate the number at all.

- **One ask per issue.** If there are five asks, that is five issues or one
  errata list with five clearly numbered items and no argument between them.
- **Evidence is linked, not inlined.** A permalink to a line range beats a
  quotation; a quotation beats a paragraph explaining the quotation.
- **State the defect, the evidence, and the fix.** Nothing else.

⚠ The 2026-08-26 filings averaged **~750 words**. The dev-portal one was a
two-sentence documentation fix in six sections. A maintainer who cannot find the
ask in fifteen seconds will not look for it.

### 3. No "positives" filings to a bug tracker

An issue tracker is for things that need doing. Appreciation is not.

⚠ **And on `rippled` it is not even accepted**: `blank_issues_enabled: false`,
with only a bug report and a feature request offered.

⚠ `rippled#8118` was *"four design decisions that were better than they
looked"*. It needed a same-day correction because its central claim was false —
the spec advertises the property **twice**, in wording close to what the filing
presented as its own reading — and a core contributor **closed it without
comment**.

**Positive observations still get captured** in `UPSTREAM-FEEDBACK.md`, and they
still hold the higher bar in `CLAUDE.md`. They reach a team through a channel
meant for them, or not at all.

### 4. No negative claim without its recorded search

*"There is no field"*, *"nothing documents this"*, *"not exported"*, *"nobody
has called this out"* — each is a claim about a whole corpus, and one search
settles it.

The search command and its result go **in the draft**, next to the claim.

⚠ Two rows died this way. **U-15** quoted a sentence XLS-0096 has never
contained. **`rippled#8118` item 1** said a property was not advertised anywhere,
and the spec states it twice. `CLAIMS.md` **P-12** and
`tools/check-negative-claims.ts` came out of the first; this rule extends the
gate to drafts.

### 5. Plain English, short sentences

The reader is a maintainer skimming a queue, and English may not be their first
language.

- Short sentences. One idea each.
- Say **`fail_hard`**, not `tapFailHard`. ⚠ Project shorthand is not an API name
  and it has escaped into a public filing once already (`CLAIMS.md` E-156).
- No rhetorical build-up, no *"interestingly"*, no *"it is worth noting"*.
- Define an abbreviation on first use or drop it.
- ⚠ **Do not carry this repository's emphasis style outward.** The warning signs
  and bold blocks are internal instruments; in a filing they read as shouting.

---

## Before sending — the checklist

1. `make check-filing FILE=<draft>` passes.
2. An adversarial review has run on the draft and every finding is resolved.
3. Every citation re-fetched at source **today**, with the ref recorded.
4. Every negative claim carries its search.
5. The Trail of Bits April 2026 review has been checked — ⚠ several things this
   project first recorded as findings were already found and fixed there.
6. The ask is one sentence and appears in the first paragraph.
7. Authorisation from the project owner **for this filing**. ⚠ Authorisation is
   never standing; it is per filing, per session.

---

## After sending

- Archive the exact submitted text under `docs/upstream-filings/<date>/`. A
  GitHub issue can be edited; the archive is what the register points at.
- Record the issue URL in `UPSTREAM-FEEDBACK.md` and move the row to `Filed`.
- ⚠ **If a correction becomes necessary, post it as a comment and leave the
  original body alone.** Editing the body makes the thread incoherent — the
  correction then refers to text that no longer exists — and GitHub shows the
  edit history publicly anyway.

---

## What this protocol does not fix

- ⚠ **It does not make a filing welcome.** Six of seven from 2026-08-26 have had
  no response after six days. That is normal for these repositories and is not
  evidence of anything, in either direction.
- ⚠ **`check-filing` is lexical.** It counts words, finds unsearched negatives by
  their common spellings, and flags long sentences. **It cannot tell whether a
  claim is true**, and a claim phrased in a way it does not recognise is
  invisible to it. The review in rule 1 is the instrument for that; this gate
  only stops the shapes that have already gone wrong twice.

## 0. First, the two cheap rejections — before any source is opened

⚠ **These cost one API call each and can end the review immediately.** Verifying
claims against primary sources and the Trail of Bits appendix is the expensive
part; do not spend it on a draft that cannot be filed anyway.

**Right venue?** Confirm the destination repository exists and is owned by the
org the draft assumes. ⚠ **Testing this on U-54 found exactly that defect** — the

to the wrong repository is still a wasted filing**, and no evidence check catches

**Right shape?** Read the target's `.github/ISSUE_TEMPLATE/` **and decode its

```sh
  --jq '.content' | base64 -d
```

⚠ **`blank_issues_enabled: false` means only the listed shapes are accepted.**
`rippled` sets it, `rippled#8118` fit neither template, and it was closed without
comment. **If the draft fits no accepted template, stop here and say so.**

---

## ⚠ Then correctness, and this is the whole point

A concision pass would not have caught **a single one** of the thirteen defects
found in the 2026-08-26 round. Every one was a claim that was **false or
overstated**, and counting words finds none of those.

**So attack the claims before you touch the prose.**

### Verify every claim against the primary source, now

- Open the source the draft cites. **Do not trust the draft's quotation** — a
  filed row once quoted a sentence the specification has never contained
  (`UPSTREAM-FEEDBACK.md` U-15).
- Check line numbers and section numbers still resolve. Sources move.
- ⚠ **Every negative claim needs its search, and you run it.** *"There is no
  such field"*, *"not called out anywhere"*, *"not exported"* — one search
  settles it. **`rippled#8118` said a property was not advertised anywhere; the
  specification states it twice**, once in wording close to what the draft
  presented as its own reading.
- Check whether upstream already fixed it. **Four rows died as stale gaps** —
  `UPSTREAM-FEEDBACK.md` U-3, U-8, U-9, U-10 — each describing something already closed.
- Check the Trail of Bits April 2026 review. Several things this project first
  recorded as findings were already found and fixed there. Read Appendices B to D
  too: the fix review does not cover them, and F-19 was in Appendix B
  (`CLAIMS.md` E-296).

### Separate the three layers

**Demonstrated** — you ran it or read it at source.
**Inferred** — it follows, but nobody checked.
**Proposed** — what the draft wants done.

⚠ A draft that presents the second or third as the first is the defect that
needed four public corrections. Say which layer each claim is on.

⚠ **Do not let the draft's framing set yours.** Ask what would have to be true
for the claim to be *wrong*, and go and check that.

## Then the maintainer's read

**Actionable?** Can a maintainer tell what to investigate, decide or change?

**Scoped?** One independently actionable problem, or several disguised as one?

**Skimmable?** Headings, bullets, code blocks, tables. Conclusion before
evidence.

**Something to do?** ⚠ A positives-only filing does not belong on a bug tracker
at all — reject it rather than editing it.

## Delete

Essay introductions, throat-clearing, praise before the report, rhetorical
questions, speculative motivation about maintainer intent, repeated conclusions,
research narration, background a maintainer already has, and any restatement of
the same point in summary and conclusion.

**Also delete, specifically for this project:** project shorthand
(`tapFailHard`), internal register references (`CLAIMS.md`, `E-nnn`,
`REVIEW-nnn`), and this repository's ⚠-and-bold emphasis style.

## Rewrite

Produce the edited version. **Aim to cut at least 20% without losing
load-bearing evidence.** If the draft is already tight, say so and do not cut
mechanically.

Run `make check-filing FILE=<draft>` on the result.

## Report

1. **Claims that did not survive verification** — with what you ran.
2. **Claims that need a search that has not been run.**
3. **Layer corrections** — demonstrated / inferred / proposed.
4. **The edited version.**
5. **Word count before and after.**

⚠ **If any claim failed verification, say plainly that the draft is not ready to
file.** Rule 1 gates on this. It is better to lose a filing than to correct one
in public.

TITLE: [Build] build-wasm.sh links C++ with emcc, which fails from emsdk 6.0.6 on
REPO: XRPLF/mpt-crypto

---

`build-wasm.sh` compiles `src/utility/mpt_utility.cpp` as C++, then links the module with plain `emcc`. From emsdk 6.0.6, `emcc` no longer links the C++ runtime by default, so the link fails with the C++ runtime missing. CI did not catch it because it pins emsdk 6.0.2, and the WASM job [passed at `3baaaac`](https://github.com/XRPLF/mpt-crypto/actions/runs/32380884181). The script's own prerequisites line names no version. On macOS arm64, every emsdk I tried from 6.0.6 on fails, and the changelog describes the change for all platforms.

**Suggested fix:** link with `em++` on the three link lines, as Emscripten's changelog recommends.

**Cause**

Emscripten's [ChangeLog for 6.0.6](https://github.com/emscripten-core/emscripten/blob/6.0.6/ChangeLog.md#L23-L25):

> `DEFAULT_TO_CXX` is now disabled by default. This means that `em++` is now required when linking C++ programs, matching the behavior of clang and gcc. The old behavior is still available using `-sDEFAULT_TO_CXX`. (#11121)

At `3baaaac`, the C++ object is compiled with `em++` ([line 272](https://github.com/XRPLF/mpt-crypto/blob/3baaaac33dadec3e649846e487f452c5b6b2d825/.github/scripts/build-wasm.sh#L272)) and linked with `emcc` ([lines 363, 365 and 374](https://github.com/XRPLF/mpt-crypto/blob/3baaaac33dadec3e649846e487f452c5b6b2d825/.github/scripts/build-wasm.sh#L363-L374)).    317	#  - WASM_BIGINT: marshal i64 <-> JS BigInt directly — mpt amounts are uint64_t.
   318	#  - ALLOW_MEMORY_GROWTH: let the heap grow on demand instead of reserving a fixed
   319	#    block up front.
   320	#  - GROWABLE_ARRAYBUFFERS=0: emsdk 6.x defaults this to 1, which grows the heap in
   321	#    place backed by a RESIZABLE ArrayBuffer. A subarray of a resizable buffer makes
   322	#    TextDecoder.decode throw in Chrome ("ArrayBuffer must not be resizable"), which
   323	#    breaks the xrpl.js browser tests. Setting 0 keeps growth but reallocates a plain
   324	#    (non-resizable) buffer on each grow — browser-safe, and no fixed memory cap.
   325	#  - MAXIMUM_MEMORY=128MB: a defense-in-depth ceiling. The real working set is small
   326	#    and stable — dominated by secp256k1's static tables, with per-op allocations
   327	#    freed and reused, so it does not grow over time — and stays far below this cap.
   328	#    The ceiling just bounds a hypothetical runaway well under the 2GB default.
   329	#  - EXPORTED_RUNTIME_METHODS: the TS marshalling layer needs HEAPU8 + ccall/cwrap.
   330	#  - ENVIRONMENT=web,node: the base .js/.mjs glues run under Node; a dedicated
   331	#    browser glue is re-linked below as web,worker (no Node branch) — see the links.
   332	LINK_FLAGS=(
   333	    -Oz -flto
   334	    "${OBJECTS[@]}"
   335	    "${SECP256K1_BUILD}/lib/libsecp256k1.a"
   336	    "${OPENSSL_SRC}/libcrypto.a"
   337	    -sMODULARIZE=1
   338	    -sEXPORT_NAME=MptCrypto
   339	    -sWASM_BIGINT=1
   340	    -sALLOW_MEMORY_GROWTH=1
   341	    -sGROWABLE_ARRAYBUFFERS=0
   342	    -sMAXIMUM_MEMORY=134217728
   343	    -sEXPORTED_FUNCTIONS="${EXPORTS}"
   344	    '-sEXPORTED_RUNTIME_METHODS=["ccall","cwrap","HEAPU8"]'
   345	    -sENVIRONMENT=web,node
   346	)
   347	
   348	# @xrplf/mpt-crypto ships dual CJS+ESM so the same package works under Node
   349	# `require`/Jest AND under bundlers/browsers via `import`. Emit THREE Emscripten
   350	# glues from the identical objects — they all wrap the SAME mpt_crypto.wasm:
   351	#   - mpt_crypto.js      : MODULARIZE CommonJS   (require()'d by the CJS build / Node)
   352	#   - mpt_crypto.mjs     : EXPORT_ES6, web+node  (Node `import`; its Node branch runs
   353	#                          `await import("node:module")` to read the .wasm from disk)
   354	#   - mpt_crypto.web.mjs : EXPORT_ES6, web only  (bundlers/browsers) — the same glue
   355	#                          built with ENVIRONMENT=web,worker instead of web,node, so it
   356	#                          carries NO Node branch and thus no `node:` imports. Browser
   357	#                          bundlers reject the `node:` URI scheme at build time even
   358	#                          though that code is dead in a browser, so the package's
   359	#                          `browser` export must point here, not at mpt_crypto.mjs.
   360	# Both ESM glues use `new URL('mpt_crypto.wasm', import.meta.url)` so bundlers
   361	# auto-emit the .wasm as an asset instead of a runtime read. Keep the three links in
   362	# lockstep — they must wrap the byte-identical module.
   363	emcc "${LINK_FLAGS[@]}" -o "${OUT_DIR}/mpt_crypto.js"
   364	wasm_sha_cjs="$(sha256_of "${OUT_DIR}/mpt_crypto.wasm")"
   365	emcc "${LINK_FLAGS[@]}" -sEXPORT_ES6=1 -o "${OUT_DIR}/mpt_crypto.mjs"
   366	wasm_sha_esm="$(sha256_of "${OUT_DIR}/mpt_crypto.wasm")"
   367	# Browser-only glue. -sENVIRONMENT=web,worker (overriding web,node) drops the Node
   368	# code path and its `node:` imports. Emscripten names the .wasm after the -o basename,
   369	# so link under the shared `mpt_crypto` name in a temp dir — the glue then references
   370	# `mpt_crypto.wasm`, the one we ship — and move just the glue out. Linking straight to
   371	# mpt_crypto.web.mjs would emit and reference a separate mpt_crypto.web.wasm.
   372	web_tmp="$(mktemp -d)"
   373	trap 'rm -rf "${web_tmp}"' EXIT
   374	emcc "${LINK_FLAGS[@]}" -sEXPORT_ES6=1 -sENVIRONMENT=web,worker -o "${web_tmp}/mpt_crypto.mjs"
   375	wasm_sha_web="$(sha256_of "${web_tmp}/mpt_crypto.wasm")"
   376	mv "${web_tmp}/mpt_crypto.mjs" "${OUT_DIR}/mpt_crypto.web.mjs"
   377	
   378	# The browser glue exists precisely so browser bundlers never see a `node:` import; the
   379	# Node smoke test can't catch a regression (Node resolves node:module fine), so assert
   380	# the invariant at build time. Matches emscripten's dynamic `import("node:…")` and any
   381	# static `from "node:…"`, but not the benign `{…,node:…}` FS object literals.
   382	if grep -Eq 'import\(["'"'"']node:|from[[:space:]]*["'"'"']node:' "${OUT_DIR}/mpt_crypto.web.mjs"; then
   383	    echo "ERROR: mpt_crypto.web.mjs leaked a node: import — browser bundlers will reject it" >&2
   384	    exit 1
   385	fi

   389	# references the shipped mpt_crypto.wasm), so enforce it.

https://github.com/XRPLF/mpt-crypto/pull/147
fix: honour proof_out capacity and validate required pointers (Zellic DEFI-1108/1109/1110)
Summary

Resolves the three findings from the Zellic scan of mpt-crypto@3baaaac (current `main`): DEFI-1108, DEFI-1109, DEFI-1110 on the DEFI board. Each was verified against the source at that commit before anything was changed.

DEFI-1110 (memory safety, the one that matters)

`secp256k1_bulletproof_prove_agg` documents `*proof_len` as the caller's buffer capacity on input, but overwrites it with `proof_size` immediately after validating `m`. The only capacity check, in the serialization block, then compares that value against a locally recomputed `expected` equal to it, so `*proof_len < expected` is dead for every supported `m`, and an undersized `proof_out` is serialized past its end.

Reproduced under AddressSanitizer on unpatched `main`: a 600-byte heap buffer with declared capacity 600 takes a heap-buffer-overflow WRITE 0 bytes after the region, in the trailing-scalar memcpy block, for an m=1 proof requiring 688 bytes (88-byte overrun). The same repro against this branch returns 0 and reports 688.

Fix: capture the capacity in a local before `*proof_len` is written, and resolve the size-query (`proof_out == NULL`), NULL-`proof_len` and insufficient-capacity paths at the top of the function, before any proving work rather than after it.

Compatibility: both in-repo callers (`mpt_get_bulletproof_agg`, reached from the Send and ConvertBack builders) already pass `kMPT_{SINGLE,DOUBLE}_BULLETPROOF_SIZE`, which equal the computed sizes for m=1 and m=2, so existing callers are unaffected. Two behaviour differences worth knowing: a size query now returns immediately without running the prover (previously it returned 1 only if proving succeeded), and on an internal proving failure `*proof_len` is left at the caller's capacity rather than set to the required size. Neither is relied on in-repo. Separately, note that `mpt_get_bulletproof_agg` only checks the written length after the call returns, so the utility layer was never itself enforcing the capacity it passes down; correct today because every caller hands it a matching constant.

DEFI-1108 (robustness)

`secp256k1_bulletproof_create_commitment` dereferenced `h_generator` and `commitment_C` without validating them, so a NULL required pointer crashed the process instead of returning the documented 0 (confirmed: SIGSEGV on unpatched `main`). Added `MPT_ARG_CHECK` entry-point checks, the idiom already used across `elgamal.c` and the proof modules. The same checks are added to `prove_agg`, which had the identical gap the scan did not flag. `context_id` is deliberately excluded: it is documented optional and NULL-guarded at every transcript absorption.

DEFI-1109 (documented, deliberately not changed)

`secp256k1_elgamal_add` / `_subtract` cannot represent an identity result, because a `secp256k1_pubkey` has no encoding for the point at infinity; subtracting a ciphertext from itself, or any pair sharing a component, returns 0 indistinguishably from a genuine failure. Giving the ciphertext an identity-capable representation changes the exported representation downstream consumers build on, so this PR documents the limitation in the API contract and pins it with tests instead. Whether to change the representation is a protocol decision, not a library one, and it is the same underlying mechanism as AXRT-4218 at the transactor layer, so the two are worth deciding together. Both functions are WASM-exported specifically for client-side chained-balance prediction (`CB_S' = CB_S -/+ the encrypted amount`), which is the path that can actually reach a cancellation, so the header now points callers at `generate_canonical_encrypted_zero()` for a zero balance.

Testing

New `tests/test_api_hardening.c`. Verified to be genuine regression tests by building the same file against unpatched `main`: the DEFI-1108 case exits 139 (SIGSEGV) and the DEFI-1110 case exits 134 (assertion), while the DEFI-1109 case passes both before and after, since it pins existing behaviour rather than changing it.

On this branch: Debug build on macOS with `MPT_CRYPTO_WERROR=ON`, 13/13 ctest pass. `pre-commit run` clean on all changed files. The `_shared` test variant is exercised only in CI.
