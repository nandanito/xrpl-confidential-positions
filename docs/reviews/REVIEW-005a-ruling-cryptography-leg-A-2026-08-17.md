# REVIEW-005 — ruling: nonce construction for XLS-0096 compact sigma proofs

- **Reviewer:** independent Cryptography Reviewer. Cold read: this packet, `ADR-0001` §(e), `cmpt-compact-sigma.pdf`, and the Trail of Bits report `2026-04 Ripple Labs XRP Ledger Confidential Transfer — Cryptographic Review (PUBLIC)`.
- **Date:** 2026-08-17.
- **Verdict:** the sketch in ADR-0001 §(e) is replaced. It was not merely underspecified — **it is wrong**, and the way it is wrong is exploitable in ordinary operation. See D-2 and §3.1.
- **Adoption ruling:** **the project specifies its own construction.** It does not adopt upstream's. Reasons in D-4.
- **Scope ruling:** the ruling below is conditional on a question the packet never asks and the ADR never answers — **who calls the nonce generator.** If the signer proves by FFI into `XRPLF/mpt-crypto`, this construction is unreachable code and the correct deliverable is a different one. See §5.1 and §6, GAP-A.
- **Not ruled on:** ElGamal key derivation from the XRPL master seed; whether proving belongs on the holder's machine. Both out of scope as instructed.

## 0. The rulings, in order of consequence

| # | Ruling |
|---|---|

It is: *every byte that can influence the Fiat–Shamir challenge, other than the first-round commitments, MUST appear injectively in the nonce-derivation preimage.*** Nonce reuse is a symptom; a nonce preimage coarser than the challenge preimage is the disease. | **D-3** | **Hedged, not deterministic — with the randomness entering as an XOR mask on the long-lived secret**, BIP-340 style, not as an HKDF salt. ## 1. The construction

### 1.1 Why this shape — the derivation of D-1

Take it from the paper's own Theorem 4.2 rather than from folklore.

Two accepting transcripts with **the same first-round commitments** `T` and **distinct challenges** `e ≠ e′` yield the witness by `w = (z − z′)/(e − e′)`. In compact form the commitments are not transmitted, so this is invisible to a verifier — the paper says so in §6.1 and the packet quotes it correctly.

Now run it forwards. `T` is a deterministic function of the nonces alone (Eqs. 2–7). The challenge `e` is a deterministic function of the full Fiat–Shamir preimage (Eq. 25). Therefore:

> **The catastrophic event is exactly: two proof instances whose nonce-derivation inputs collide while their Fiat–Shamir preimages differ.**

That gives the requirement directly. Let `FS(instance)` be the challenge preimage minus the commitment block, and `N(instance)` the nonce preimage. The construction is safe iff

```
N(i) = N(j)   ⟹   FS(i) = FS(j)
```

i.e. **the nonce preimage refines the challenge preimage.** The easiest way to guarantee that is to make `FS` a literal substring of `N`, injectively framed. That is what §1.3 does.

Note the converse is a non-event: if `N(i) = N(j)` *and* `FS(i) = FS(j)`, both instances produce the same commitments, the same challenge, and the same responses — a byte-identical proof. Emitting the same proof twice reveals nothing. **This is why a purely deterministic construction is safe at all, and it is also why "the nonces repeated" is the wrong thing to test for.** The thing to test for is `T` colliding across differing preimages (§4, T-3 and T-9).

### 1.2 Primitives and constants

```
Hash            SHA-512               (FIPS 180-4)
MAC             HMAC-SHA-512          (RFC 2104)
KDF             HKDF-SHA-512          (RFC 5869)
Tagged hash     TH(tag, msg) := SHA-512( SHA-256(tag) ‖ SHA-256(tag) ‖ msg )
Group order     q = 0xFFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFE BAAEDCE6 AF48A03B BFD25E8C D0364141

LABEL    := "CMPT-NONCE"                       10 bytes, ASCII: 43 4D 50 54 2D 4E 4F 4E 43 45
VERSION  := 0x01                               1 byte
SALT     := SHA-256(LABEL ‖ VERSION)           32 bytes, fixed and public
         =  374e013f8714020a88570fb12d7af8b4c3e1d915b5fd2e13226d9274a993f332
AUX_TAG  := "CMPT-NONCE/v1/aux"                17 bytes, ASCII
```

Encoding helpers, all big-endian, no exceptions:

```
u8(n)        1 byte
u16be(n)     2 bytes
u32be(n)     4 bytes
scalar32(x)  32 bytes, big-endian, x ∈ [0, q). Zero encodes as 32 × 0x00.
point33(P)   SEC1 compressed, 33 bytes, first byte 0x02 or 0x03.
             The identity has no encoding. If any statement element is the identity, ABORT.
```

### 1.3 Step 1 — the Fiat–Shamir prefix `FS_PREFIX`

`FS_PREFIX` is the challenge preimage for this proof, **with the domain tag removed from the front** (it is carried separately, framed, in the IKM) **and the first-round commitment block removed** (it depends on the nonces; including it would be circular). Everything else survives, including `TransactionContextID`.

```
FS_PREFIX := u16be(ELEM_COUNT) ‖ for each element e in order: u8(KIND_e) ‖ u32be(len_e) ‖ bytes_e

KIND: 0x01 = compressed point (len MUST be 33)
      0x02 = opaque byte string (TransactionContextID)
```

No bare concatenation appears anywhere. Element count is framed, every element is length-framed, and every element carries a kind tag. This is what makes the encoding injective under a future field addition (item 7).

### 1.4 Step 2 — the masked long-lived secret

```
aux      : exactly 32 bytes, supplied by the caller (see §2.2)
mask     := TH(AUX_TAG, aux)[0..32]
sk_star  := scalar32(sk) XOR mask                 (sk = sk_A, or sk_iss for Clawback)
```

`sk` MUST be in `[1, q)`; otherwise ABORT. **The long-lived secret appears in the derivation preimage exactly once, and only in masked form.** It is never included raw.

### 1.5 Step 3 — IKM, extract, expand

```
IKM :=  LABEL                                     (10)
     ‖  VERSION                                   (1)
     ‖  u8(PROOF_TYPE_ID)                         (1)
     ‖  u32be(len(DOMAIN_TAG)) ‖ DOMAIN_TAG       (ASCII, no NUL, byte-identical to the tag used in the FS hash)
     ‖  u32be(len(FS_PREFIX))  ‖ FS_PREFIX
     ‖  u8(K)                                     (number of witness slots)
     ‖  for j = 0 .. K-1:  u8(j) ‖ u8(SLOT_KIND_j) ‖ VALUE_j     (32 bytes each)

SLOT_KIND: 0x00 = plain scalar        VALUE = scalar32(w_j)
           0x01 = masked long-lived   VALUE = sk_star

PRK := HKDF-Extract(salt = SALT, ikm = IKM)       = HMAC-SHA-512(SALT, IKM)      → 64 bytes

for j = 0 .. K-1:
    info_j := LABEL ‖ VERSION ‖ u8(PROOF_TYPE_ID) ‖ 0x6E ‖ u8(j) ‖ u8(len(NONCE_LABEL_j)) ‖ NONCE_LABEL_j
    okm_j  := HKDF-Expand(PRK, info_j, 64)        = HMAC-SHA-512(PRK, info_j ‖ 0x01)      → 64 bytes
    α_j    := int_be(okm_j) mod q
    if α_j == 0: ABORT
```

`0x6E` is ASCII `n`, reserving the info namespace so a future non-nonce use of the same PRK cannot collide.

Each nonce is its own single-block Expand with a distinct `info`. They are not chained. Independence is HMAC's PRF property under distinct inputs with a secret key, which is the standard assumption already relied on for `PRK` itself.

### 1.6 Per-proof-type table (checklist item 4)

**Derivation order rule, stated once so it is checkable rather than remembered: the witness order is the serialisation order of the corresponding `z` values in the compact proof.** That order is verifiable against the wire format and against the header constants, which a prose ordering is not. The paper is internally inconsistent here — §8.3 gives the ConvertBack witness as `(b, sk_A, ρ)`, samples nonces as `(t_b, t_sk, t_ρ)`, and serialises `Π_cb = (e, z_b, z_ρ, z_sk)`. The rule picks the third. It agrees with the packet's C-1 and disagrees with the paper's prose; the disagreement is harmless (C-6) but must not be left to an implementer's reading.

| Type | `PROOF_TYPE_ID` | `DOMAIN_TAG` | `FS_PREFIX` elements, in order | K | Witness slots, in order | Nonce labels |
|---|---|---|---|---|---|---|
| **Send** | `0x01` | `CMPT_SEND_SIGMA` | `P₁ … Pₙ`, `P_A`, `C₁`, `C₂,₁ … C₂,ₙ`, `PC_m`, `PC_b`, `B₁`, `B₂` (all `KIND 0x01`), then `TransactionContextID` (`KIND 0x02`) | 5 | `m`(plain), `r`(plain), `b`(plain), `ρ`(plain), `sk_A`(**masked**) | `send/alpha_m`, `send/alpha_r`, `send/alpha_b`, `send/alpha_rho`, `send/alpha_sk` |
| **ConvertBack** | `0x02` | `CMPT_CONVERTBACK_SIGMA` | `P_A`, `B₁`, `B₂`, `PC_b`, then `TransactionContextID` | 3 | `b`(plain), `ρ`(plain), `sk_A`(**masked**) | `convertback/t_b`, `convertback/t_rho`, `convertback/t_sk` |
| **Clawback** | `0x03` | `CMPT_CLAWBACK_SIGMA` | `P_iss`, `C₁`, `C₂`, `m·G` (compressed point), then `TransactionContextID` | 1 | `sk_iss`(**masked**) | `clawback/t_sk` |
| **Registration PoK** | `0x04` | `CMPT_POK_SK_REGISTER` | **PROVISIONAL — see GAP-B** | 1 | `sk`(**masked**) | `register/t_sk` |

Sources: Send from Eq. (25); ConvertBack from Eq. (31); Clawback from §8.2 prose. Registration is not covered by the paper at all — §6, GAP-B.

Note that `n` needs no separate encoding: `ELEM_COUNT` is framed and each `P_i` is a separate framed element, so `n = 3` and `n = 4` statements cannot collide.

**There is deliberately no Convert row.** Per §8.1, production Convert carries a mandatory `BlindingFactor` field containing `r` and is verified deterministically; **no sigma proof is defined for it.** The packet's C-1 is right to omit it. This matters for a different reason: Convert's `r` is *published*, so any implementer tempted to share a randomness cache between Convert and Send would publish a value that must stay secret in Send. Stated so nobody has to rediscover it.

## 2. The packet's checklist, item by item

The cover instruction says "Section 6 of the packet lists ten items". Packet §6 is *Context on the runtime*; the checklist is **§4, and it has twelve items**. Given §9's revision history, this suggests the cover note was written against an earlier draft. I have answered §4's twelve. Flagging it because a review packet that miscounts its own deliverable is exactly the artifact class this ADR exists to be careful about.

**1. KDF and primitive.**
HKDF-SHA-512 (RFC 5869), i.e. HMAC-SHA-512 in extract-then-expand. Chosen because: (a) SHA-512's 64-byte block is exactly the width needed for a single-block wide reduction per nonce, so no output chaining and no counter; (b) HKDF's extract/expand split gives a clean place to put per-nonce domain separation (`info`) that is structurally separate from the secret input (`IKM`); (c) RustCrypto `hkdf` + `sha2` are mature, `no_std`-capable, and already in the dependency shape a signer will have. SHA-256 appears only inside `TH` for the aux mask and in the fixed `SALT`, both non-secret paths.

Not RFC 6979 as such. RFC 6979 is a *deterministic ECDSA nonce* spec with an internal HMAC_DRBG loop and a rejection counter; adopting it here would import the retry-desync problem (item 9) for no benefit, since we are not interoperating with anything (C-6). The paper's Remark 6.1 says "RFC 6979 in spirit" and that is the right reading — spirit, not letter.

**2. Randomness.**
**Yes, the construction consumes randomness: exactly 32 bytes, once per proof, as the `aux` parameter.** It enters at §1.4, before any hashing, as an XOR mask over the long-lived secret only.

*Where from:* the OS CSPRNG and nothing else — `getrandom(2)` on Linux, `getentropy(2)` on macOS, `BCryptGenRandom` on Windows. In Rust: the `getrandom` crate directly. **Not** `rand::thread_rng()`, **not** any seeded or user-space RNG, **not** `/dev/urandom` via file I/O (fd exhaustion returns success on a closed fd in some failure modes).

*On failure:* **hard abort.** The daemon returns an error, emits no transaction, and does not retry in-process. There is no zero-fallback path, no cached-entropy path, and no "try the other source" path compiled into the release binary.

*The one permitted zero-aux path:* `aux = 0x00 × 32` is a legal input to the derivation function — it must be, or the known-answer vectors in Appendix A cannot exist. It is reachable only from tests and from a build compiled with the `kat-vectors` feature, which also refuses to sign or submit. Enforce with `#[cfg(...)]` on the submit path, not with a runtime flag.

*The single call site.* Exactly one function in the whole signer calls `getrandom`. CI greps for any other occurrence of `getrandom|rand::|thread_rng|urandom` outside that module and fails the build. This is the only mechanism that makes "silent fallback is impossible" a checkable property rather than an intention.

**3. Domain and version labelling.**
Bytes are in §1.2. Three separations, deliberately redundant:
- `SALT = SHA-256(LABEL ‖ VERSION)` separates the whole construction from any other HKDF use in the codebase.
- `VERSION ‖ PROOF_TYPE_ID ‖ framed DOMAIN_TAG` inside `IKM` separates proof types.
- `VERSION ‖ PROOF_TYPE_ID ‖ 'n' ‖ index ‖ framed label` inside `info` separates nonce positions.

*Migration rule.* **Any change to the layout — a new field, a reordering, a width change, a new proof type that reuses an existing tag — increments `VERSION`.** Because `VERSION` feeds `SALT`, the `IKM`, and every `info`, a v1 and a v2 derivation cannot produce the same `PRK` for any inputs, so old and new encodings can never collide. Old versions are deleted rather than kept: there is nothing to be backward-compatible with (C-6), and keeping a v1 path alive is a way to reintroduce the very collision the versioning prevents.

*Related, and worth knowing:* Trail of Bits **TOB-RIPCTX-3** (Informational, Resolved) found two structurally different proof systems in `mpt-crypto` sharing the tag `MPT_POK_SAME_PLAINTEXT_PROOF`, and a link proof using a generic tag where the spec defines Variant A (`_R`) and Variant B (`_SK`). The long-term recommendation was a systematic naming convention enforced by automated checks. The convention above is that, applied to our layer.

**4. Per-proof-type table.** §1.6.

**5. Canonical encoding of witness elements.**
All witness elements are `scalar32`: 32 bytes, big-endian, value in `[0, q)`. A scalar that is zero encodes as 32 zero bytes — the encoding has no special case. **What has a special case is admissibility:**

| Element | May be zero? | Why |
|---|---|---|
| `m` (amount) | **Yes** | A zero-amount Send is legal, and §(b) notes a zero-amount Convert is a valid key registration. |
| `b` (balance) | **Yes** | An empty confidential balance is a legal state. |
| `r` (shared ElGamal randomness) | **No — ABORT** | `r = 0` gives `C₁ = 𝒪` and `C₂,ᵢ = m·G` for every recipient. Every amount becomes recoverable by anyone via the same bounded DLP search the library already implements (`secp256k1_solve_dlp_small_range_ct`, TOB-RIPCTX-1). Total loss of amount confidentiality, no proof pair required. |
| `ρ` (Pedersen blinding) | **No — ABORT** | `PC_b = b·G` is an unblinded commitment to the balance; same bounded search recovers `b`. |
| `sk_A`, `sk_iss` | **No — ABORT** | Not a valid key. Must be in `[1, q)`. |

Statement points: `point33`. **The identity is inadmissible** and MUST abort rather than encode — note TOB-RIPCTX-6's fix history, where a multiscalar multiplication landing on the point at infinity had to be surfaced in a return value.

**6. Canonical encoding of the statement.**
§1.3 and the table in §1.6. Points are SEC1 compressed, 33 bytes, prefix `0x02`/`0x03`, in the order given by the challenge equation for that proof type.

*How transaction context binds in.* As the final `FS_PREFIX` element, `KIND 0x02`, length-framed. **This is the item the ADR sketch gets wrong and it deserves its own paragraph.** From `rippled/src/libxrpl/protocol/ConfidentialTransfer.cpp` as quoted in TOB-RIPCTX-15:

```
getConvertBackContextHash(account, sequence, issuanceID, amount, version):
    addCommonZKPFields(s, ttCONFIDENTIAL_CONVERT_BACK, account, sequence, issuanceID)
    s.add64(amount); s.addInteger(version); return s.getSHA512Half()
```

So `TransactionContextID = SHA512Half(txType ‖ account ‖ **sequence** ‖ issuanceID ‖ TxSpecific)`. **The account sequence number is inside it. The statement points are not functions of the sequence number.** Consequences in §3.1.

Also from that finding: the specification's `TxSpecific` notation and the implementation's disagreed for Convert and ConvertBack until the fix. The context hash is a documented drift surface. **The signer MUST reproduce `TransactionContextID` from rippled's construction, not from the spec's prose, and MUST have a test vector pinning it** — which is precisely what Trail of Bits recommended long-term and which, as far as this review can tell, does not yet exist upstream.

**7. Length framing.**
Every variable-length field carries a `u32be` length; every fixed field has a stated width; `FS_PREFIX` carries an element count and a per-element kind tag; `IKM` carries a witness-slot count and per-slot index. Ambiguity under future field addition is handled by `VERSION` (item 3), not by hoping the framing is future-proof.

Verified rather than asserted: `fs_prefix([("AB"), ("C")]) ≠ fs_prefix([("A"), ("BC")])` — see §4, T-6.

For context on why this is not paranoia: **TOB-RIPCTX-17** (Low, Resolved) found four helpers in `ConfidentialTransfer.cpp` slicing and `memcpy`-ing buffers without length validation, safe only because callers happened to have checked. Length discipline in this codebase has a history.

**8. Expansion.**
One HKDF-Expand call per nonce, 64 bytes each, distinct `info` per nonce carrying the version, proof type, positional index and a fully qualified label. No chaining between nonces, so a bug in one cannot propagate. Independence rests on HMAC-SHA-512 being a PRF under the secret `PRK`, which is the same assumption that makes `PRK` itself usable; nothing weaker is being asked of it.

**9. Mapping into the scalar field.**
**Wide reduction. `α = int_be(okm‖64 bytes) mod q`. No rejection sampling, no retry, no counter.**

*Bias.* For `X` uniform on `[0, 2⁵¹²)` and `q < 2²⁵⁶`, the statistical distance of `X mod q` from uniform on `ℤ_q` is at most `q / 2⁵¹² ≈ 2⁻²⁵⁶`. Negligible under any reading. RFC 9380's hash-to-field guidance would accept 48 bytes; 64 is used because it is one SHA-512 block.

*On zero:* **abort, do not retry.** `α = 0` gives `T = 𝒪` and `z = e·w`, so `w = z/e` with `e` public — an instant, total witness disclosure. Its probability under wide reduction is ≈ `2⁻²⁵⁶`, so **an abort here is not an unlucky draw, it is proof of a broken implementation**, and retrying would convert a loud bug into a quiet one.

*Directly answering the item's sub-question:* there is no counter to advance, because there are no rejected candidates. **The desynchronisation failure mode the packet is worried about is removed rather than specified.** This is the one place where I am deliberately diverging from upstream, which reduces a 32-byte HMAC-SHA-256 output mod `q` and retries with an extra counter byte up to 256 times. To be fair to upstream: its bias is `≈ 2⁻¹²⁷`, which is not a defect and not exploitable. The retry counter is the part worth removing, not the reduction.

**10. Memory hygiene.**
Zeroise, in this order, before the function returns on **every** path including error paths: `okm_j` buffers, the wide integers, `PRK`, the `IKM` buffer (it holds `m`, `r`, `b`, `ρ` in the clear), `sk_star`, `mask`, and `aux`. The `α_j` values are zeroised by the caller once the responses `z_j` are computed and the `α` are no longer needed.

Rust specifics, because this is where the ADR's "a Rust FFI wrapper responsibility" hand-wave turns into real bugs:
- `IKM` is built into a `Zeroizing<Vec<u8>>` allocated with `Vec::with_capacity(exact_len)` computed up front. **A `Vec` that reallocates leaves an un-zeroised copy of the witness on the heap.** Compute the length; do not push and grow.
- Witness and key types: `#[derive(Zeroize, ZeroizeOnDrop)]`, and **no `#[derive(Debug)]`** — implement `Debug` manually to print a redaction. One `dbg!` in a hurry is all it takes.
- No `format!`, `to_string`, `hex::encode`, `serde` derive, or `tracing` field on any secret-bearing type.
- `setrlimit(RLIMIT_CORE, 0)` at daemon start. `mlock`/`mlockall` best-effort with the failure logged, not asserted — it is not reliable and pretending otherwise is worse than not doing it.
- **Verify, do not assume, that the chosen `hmac`/`hkdf` crate zeroises its internal key state on drop.** If it does not, wrap it. This is a concrete, checkable task, not a note.
- The C boundary: if any of this crosses into `mpt-crypto`, zeroisation on the C side is out of our hands entirely. See §5.1.

**11. Failure behaviour.**
Every one of these is a hard abort — no fallback, no retry, no degraded mode:

CSPRNG returns an error · `aux` is not exactly 32 bytes · any statement element fails to parse as a compressed point, or is the identity · `sk ∉ [1, q)` · `r = 0` or `ρ = 0` · any witness scalar `≥ q` · witness arity ≠ the table's `K` for that proof type · domain tag contains `0x00` or does not match the table · a derived `α = 0` · any length field would overflow.

Mechanically enforced, not documented:
- One error type, carrying **no** secret material and no input echo. The daemon maps it to an opaque HTTP 500 with a code.
- Nonces are a newtype with a **private** constructor reachable only through the derivation function, so no other code path can manufacture one.
- `clippy.toml` `disallowed-methods` for RNG APIs, plus the CI grep from item 2.
- The abort is logged as a fault event with the proof type and nothing else.

**12. A test plan that can actually fail.** §4. The packet's trap in this item is real and is answered directly by T-5.

**Then answer explicitly: deterministic or hedged?**

**Hedged**, in the masking shape of §1.4. The reasoning is in §3.2, but the short version is that the packet's three arguments against hedging do not survive contact with this system: two of them describe a system this is not, and the third is neutralised by where the randomness is inserted.

## 3. Failure analysis

### 3.1 What breaks the sketch in ADR-0001 §(e) — the actual bug

ADR §(e) reads:

```
(α_m, α_r, α_b, α_ρ, α_sk) ← HKDF(sk_A ‖ r ‖ m ‖ b ‖ ρ ‖ statement ‖ fresh entropy)
```

"statement". The paper defines the public statement for the balance relation as `x = (P_A, B₁, B₂, PC_b, H)` (§8.3), and for Send as the ciphertext and commitment family (§2.1). **`TransactionContextID` is in neither.** It is listed separately, as item 4 of §6.2's *Fiat–Shamir* inputs and as the final term of Eqs. (25) and (31). A careful implementer reading §(e) and the paper together will derive nonces from the statement and omit it.

Now the exploitation path, which requires no attacker:

1. Holder signs a `ConfidentialMPTSend`. Witness `(m, r, b, ρ, sk_A)`; statement points `P_i, C₁, C₂,ᵢ, PC_m, PC_b, B₁, B₂`.
2. The transaction does not apply — queued behind another transaction, `tefPAST_SEQ`, a stuck earlier submission, a wallet retry, anything routine.
3. The client resubmits **the same transfer** at a **new sequence number**.
4. `TransactionContextID` changes, because `addCommonZKPFields` puts `sequence` inside it. **The statement points do not change** — none of them is a function of the sequence.
5. If the signer reuses the built ciphertexts (the natural optimisation: proof generation is the expensive step, and the ADR's own benchmark note treats Bulletproof timing as material), the nonce inputs are identical and the nonces repeat.
6. Two proofs. Same `T`. Different `e`. Theorem 4.2 applies. `sk_A` falls out by subtraction.
7. Nothing fails. Both proofs verify. No error code, no telemetry, no failing transaction. The ADR's own sentence — *"produces no failing transaction, no error code, and nothing an observer harness can see"* — describes exactly this, and the ADR's own proposed construction is what causes it.

This is why the verdict is "wrong", not "underspecified". D-2 fixes it by putting `TransactionContextID` in the preimage. D-7 keeps it fixed by making one encoder serve both the nonce preimage and the challenge preimage, so a field cannot be in one and not the other.

**Upstream implication.** The paper's Remark 6.1 justifies the construction with *"Including the full witness ensures nonces are unique per transaction."* That justification is **false**, and this is the counterexample: the witness is byte-identical across a resequenced resubmission while the transaction, and therefore the challenge, is not. The recommendation in Remark 6.1 is fine; its stated reason is not, and a reader who trusts the reason will build the bug. This belongs in `UPSTREAM-FEEDBACK.md` as a specific, citable correction to §6.1 — with the observation that upstream is *incidentally* protected because its implementation is hedged with a random salt despite the function being named `generate_deterministic_nonces`, so the paper's error is masked by the code's behaviour rather than absent from it.

### 3.2 What a weak or absent RNG does

Four cases, exhaustively.

| RNG state | Effect on this construction |
|---|---|
| **Errors / unavailable** | Hard abort at the single call site. No proof, no transaction. |
| **Dead — returns constant bytes** | `mask` is constant, so `sk_star` is a fixed function of `sk`. The construction degrades **exactly** to its deterministic core, which is safe under D-1. No new failure mode. |
| **Predictable — attacker knows `aux` but not `sk`** | Attacker learns `mask`. `sk_star = sk XOR mask` is still unknown to them. They cannot force a nonce collision across differing `FS_PREFIX` values, because `FS_PREFIX` is hashed in. They can force a collision across *identical* `FS_PREFIX` values, which produces a byte-identical proof — a no-op (§1.1). |
| **Adversarially chosen AND `sk` known** | Already game over for reasons unrelated to nonces. |

**Therefore: there is no RNG failure mode under which this construction is worse than a purely deterministic one.** That confirms the claim the packet struck in §5 on 2026-08-17 — **the strike was correct** — but the packet's framing of it as a general truth about hedging is not. It is a property of *where the randomness enters*:

- Randomness as an **XOR mask on the secret before hashing** (this construction, BIP-340): degrades to deterministic. Never worse.
- Randomness as an **HKDF salt** (upstream): degrades to deterministic. Never worse. Also fine.
- Randomness that **replaces** deterministic material — `α ← RNG()` directly, or `α = H(aux)` with no witness input: catastrophically worse under a degraded RNG. This is the ordinary ECDSA/Schnorr nonce failure that has emptied wallets for a decade.

So the earlier draft's claim was false as written but was pointing at something true about a third construction shape. **Making the degradation property a design requirement rather than a debating point is the right resolution**, which is what D-3 does.

*Why the masking form over the salt form,* given both degrade safely: masking keeps the long-lived secret out of the hash preimage entirely, so an adversary who obtains the preimage through a memory disclosure, a core dump, or a side channel on the hash compression function does not thereby obtain `sk_A`. It costs one SHA-512 call.

*Why hedging at all, for this runtime specifically* — answering packet §6, which asks whether the localhost-daemon placement changes the recommendation. **Yes, and toward hedging.** A purely deterministic prover gives a same-host attacker a re-runnable oracle: run once cleanly, run again with a fault injected during the response computation, and you have two transcripts sharing `T` with differing outputs. Hedging removes the "same nonce on re-run" property that fault attacks need. And a same-host adversary is *already inside this system's threat model* — REVIEW-003b's MEDIUM finding on the localhost boundary says any same-host process can forge an `Origin` header, and TOB-RIPCTX-5 (Partially Resolved) documents Bulletproof generation timing that varies with a secret-derived Hamming weight, exploitable by "an external attacker with precise timing observation over the prover's local execution environment." The ADR cannot simultaneously hold that a local adversary is plausible enough to worry about for timing and implausible enough to ignore for fault re-runs.

### 3.3 What an implementer is most likely to get wrong

Ranked by probability × damage.

1. **Omitting `TransactionContextID`.** §3.1. Caught by T-3 and T-9.
2. **Writing this construction and then never calling it**, because the proof is generated by `mpt-crypto` which derives its own nonces internally. See §5.1 — this is the most likely outcome of the current plan and no test in this document catches it.
3. **Reusing a cached proof or cached `r` across a resubmission.** The mitigation is not only in the derivation: the signer MUST rebuild the entire proof bundle whenever any byte of `FS_PREFIX` changes, and MUST NOT hold a proof cache keyed on anything coarser. Caught by T-9.
4. **Two encoders drifting.** Someone writes `serialize_for_challenge` and `serialize_for_nonce` separately, and a later field lands in one. D-7 makes this structurally impossible; without it, nothing catches it. Caught by T-3's bit-flip sweep only if the field is present in `FS_PREFIX` at all.
5. **A non-CSPRNG.** `SmallRng`, or a seeded `StdRng` that leaked from a test harness into a release path. Caught by T-5 and the CI grep.
6. **Zeroisation defeated by `Vec` reallocation.** Item 10. Not caught by any test — this is a code-review item, which is why it is stated as "compute the capacity" rather than "remember to zeroise".
7. **Debug output.** A `#[derive(Debug)]` on the witness struct plus one `tracing::debug!` in a bad week.
8. **Deriving from the serialised transaction instead of `FS_PREFIX`.** Superficially safer — it contains the sequence! — but it is a *different* set from the challenge preimage, so D-1 is not established and the equivalence has to be re-proved every time either changes. Use `FS_PREFIX`.
9. **Encoding `m·G` for Clawback as a scalar rather than a compressed point.** The paper is explicit that it is serialised as a 33-byte compressed point; the name invites the mistake.

### 3.4 The packet's rollback question, answered

*"How should either choice behave under VM snapshot rollback, or any environment that can replay a signer's state?"*

Rollback is safe for this construction, and the reason generalises into a requirement.

- Rollback that replays the *same* inputs and re-draws `aux`: new nonces, but also the same `FS_PREFIX`, so at worst you get a second valid proof of the same statement with different nonces. Two proofs, different `T`, no shared commitments, nothing extractable.
- Rollback that replays the same inputs *and* the RNG state, so `aux` repeats: byte-identical proof. A no-op.
- Rollback where the witness or statement changed but the nonce input did not: **impossible under D-1**, because the nonce input contains the entire challenge preimage.

The requirement this yields: **the construction must be stateless.** No persistent counter, no monotonic file, no "nonces used" database, no PRK cached across calls. Any of those would make correctness depend on state that a snapshot can rewind, and would reintroduce exactly the class of bug that rollback threatens. D-6 states this as a property; it is worth noting that a stateful RFC 6979-style retry loop, or a runtime "have I emitted this `T` before" cache, would both violate it. That is a second reason to prefer wide reduction over rejection sampling, and the reason the duplicate-`T` check in §4 is a **test-only** harness rather than a runtime guard.

## 5. What is wrong, missing, or steering in the packet

The packet is unusually good and §9 is an honest document. Three of the five defects it lists were real and the fixes are right. What follows is the sixth, plus what else did not survive a cold read.

### 5.1 The sixth — the packet asks for a construction the project cannot install

**The packet never establishes that the signer generates these nonces at all, and its own Appendix A contains the fact that it probably does not.**

Appendix A, on `XRPLF/mpt-crypto`: *"No exported entry point lets a caller influence the nonce — no seed argument, no RNG hook, no global."* ADR §(a) decides for a native build because *"A native build is the path mpt-crypto already supports."* ADR §(e) defers zeroisation as *"a Rust FFI wrapper responsibility."* The project instructions name *"any binding to XRPLF/mpt-crypto"* as the expected shape.

Read together, the plan is: **the Rust signer calls `mpt-crypto`'s prove functions over FFI, and `mpt-crypto` derives the nonces internally, by a route no caller can influence.** If that is right, then §1 of this ruling is unreachable code. The packet demands a construction *"specified so completely that a Rust implementer makes no judgement calls"* without ever saying whether that implementer is writing a prover or a binding — and those need different deliverables.

The shape of this defect is the same as the five in §9: a fact that would redirect the review sits in the packet, placed last, under a heading that says **"Read this last, and only if you want it."** Defect #1 in §9 was fixed by moving the upstream description *after* the requirements. That move solved the steering problem and created this one — the fact that the upstream implementation is not merely a precedent but is *the thing that will actually be running* is now filed under optional reading.

**What follows, concretely:**

- **Branch A — the signer proves by FFI into `mpt-crypto` (most likely, on the evidence).** §1 is not implementable and should not be implemented. The real deliverables become: (i) verify what upstream's 32-byte `statement_hash` actually covers, and specifically **whether it includes `TransactionContextID`** — if it does not, §3.1's bug exists upstream and is masked only by the random salt; (ii) verify that the salt reaches a real CSPRNG on every target, including the WASM path; (iii) impose the guard we *can* impose at our layer — never resubmit a cached proof, always rebuild on any `FS_PREFIX` change; (iv) run T-9 against upstream's prover, which upstream itself cannot do because it has no such test (`UPSTREAM-FEEDBACK` U-30). ADR §(e)'s nonce paragraph should then be rewritten from *"Requirement on the signer"* — a requirement we have no power to impose — to a statement of what we verified about someone else's code and what we guard at our boundary. **That is a materially different ADR section than the one this review was convened to produce.**
- **Branch B — the project writes its own prover in Rust.** §1 applies in full, and the scope of what needs specifying is larger than nonces (§5.2).

I am not able to determine which branch is real from what I was given. It is GAP-A and it blocks the ruling's applicability, not its correctness.

### 5.2 Missing: the review is scoped to `α` and the signer generates more than `α`

Nonce derivation is not the only place the signer produces a secret scalar, and the packet's scope makes the others invisible. From the ADR's own sketch, `r` and `ρ` are *inputs* to the derivation — treated as given, with nothing anywhere saying where they come from.

- **`r`, the shared ElGamal randomness.** A repeat of `r` across two Sends gives identical `C₁ = r·G` on chain. Every observer can then compute `C₂,ᵢ − C₂′,ᵢ = (m − m′)·G` and learn amount differences — and because Convert publishes `m` in plaintext and `r` in the `BlindingFactor` field, one linkable Convert can turn differences into absolute amounts. **This needs no second proof, no adversary, and no cryptographic effort: a passive chain observer gets it.** In that specific sense a repeated `r` is a *cheaper* failure than a repeated `α`, even though it is less total.
- **`ρ`, the Pedersen blinding factor.** A repeat leaks balance differences by the same argument.
- **The aggregated Bulletproof's randomness.** Bulletproofs carry their own blinding and inner-product nonces; reuse there leaks too, and it is the largest and least reviewed part of the proof bundle.

The paper notes that `mpt_internal.h` ships a shared helper `generate_random_scalar` — a direct RNG call. Hardening `α` to the byte while `r` comes from a bare `generate_random_scalar` is a false sense of completion. **Whatever construction governs `α` must govern every secret scalar the signer produces**, with the same admissibility rules (§ item 5) and the same single-call-site RNG discipline. This is a widening of the review, not a defect in the answer, and it should be recorded as such.

### 5.3 Wrong: C-6 is true and is doing the same job §9's defect #1 did

C-6 says nonce derivation is prover-local, invisible to validators, and cannot affect verification. True, and correctly derived. But the packet then draws a broader conclusion — *"There is no compatibility argument here"* — and instructs the reviewer to hold that in mind throughout.

There is no compatibility argument **about the derivation**. There is a very large one about **the proof format the derivation feeds**, and C-6 primes a reviewer to stop asking. The paper's §8.5 is explicit that compact form *"must be gated behind an XRPL amendment"* and that during transition validators accept both forms. C-1's nonce counts (5 / 3 / 1 / 1) and sizes (192 / 128 / 64 / 64 B) are the **compact-form** numbers. The shipped commitment-form multi-ciphertext equality proof is a different size entirely — `33(1+N) + 64`, i.e. 196 bytes at N=3 — and TOB-RIPCTX-16's exploit scenario is precisely a client that builds the wrong-sized proof and is rejected at preflight with *"no path to recovery."*

So: **if devnet rippled 3.3.0 accepts only commitment-form proofs, the per-proof-type table in §1.6 has the wrong rows.** The construction generalises without change — add a row, a type ID, and labels — but the table would be describing proofs the signer never builds. GAP-C.

### 5.4 Wrong: the citation in Appendix A

Appendix A: *"The 16-byte length-prefix preamble answers **TOB-RIPCTXR-10**, which upstream documents as a brittle-API concern rather than a live exploit."*

Two errors. The finding prefix is **TOB-RIPCTX**, not TOB-RIPCTXR. And **TOB-RIPCTX-10 is "Missing range proof enables confidential balance overdraft"** — severity High, difficulty Low, an unbacked-token-minting bug, since Resolved. It is not a brittle-API concern and has nothing to do with length prefixes.

The finding being described is **TOB-RIPCTX-17**, "Missing input length validation in low-level cryptographic helper functions" (Low, Resolved) — and even that targets `rippled/src/libxrpl/protocol/ConfidentialTransfer.cpp`, not `mpt-crypto`'s nonce derivation, so the claim that upstream's preamble "answers" it is at best an inference. The finding that *is* directly on point for this construction — **TOB-RIPCTX-3, "Fiat-Shamir domain tag considerations"**, which found two proof systems sharing a domain tag and recommended a systematic enforced naming convention — is not cited anywhere in the packet.

In a document whose entire premise is byte-exactness, a misattributed audit finding is not cosmetic. It should be corrected in `CLAIMS.md` wherever E-48/E-55 depend on it.

### 5.5 Also worth fixing

- **C-4 will be misread.** *"The signer must never accept caller-supplied randomness across its localhost interface"* is correct and should stay. But a literal implementer will bury the `getrandom` call inside the derivation function to comply, which destroys known-answer testability and makes T-5(a) impossible to write. Add the clarifying half-sentence: the prohibition is on the **HTTP boundary**, not the internal function signature.
- **ConvertBack witness order.** C-1 says `(b, ρ, sk_A)`; the paper's §8.3 relation says `(b, sk_A, ρ)` and its nonce sampling says `(t_b, t_sk, t_ρ)`, while its serialisation says `(e, z_b, z_ρ, z_sk)`. C-1 agrees with the serialisation. Harmless under C-6, but the packet presents it as sourced from the paper when the paper says three things.
- **The §4 / §6 numbering mismatch** between the cover instruction ("Section 6… ten items") and the packet (§4, twelve items). Noted in §2.
- **§5 is still, mildly, steering** — one paragraph for hedging, one longer against, and item 12 warns only about the hedged failure mode with no equivalent warning that a deterministic construction whose preimage is coarser than the challenge preimage fails *catastrophically and unconditionally*. §9 records that the two legs disagreed about direction. On a cold read the residual lean is toward deterministic. It did not change the answer, but it is there.
- **The framing invites elaboration rather than checking.** "Not implementable as written" and "produce the construction that replaces it" both point at completeness. The sketch's defect is not completeness — it is that `statement` is the wrong input set (§3.1). A reviewer who dutifully filled in twelve items around `HKDF(sk_A ‖ r ‖ m ‖ b ‖ ρ ‖ statement)` would ship the bug with every box ticked. Worth recording as a lesson about how review packets should state the ask: *"specify this completely"* and *"check whether this is right"* are different requests, and the first one crowds out the second.

## Verification notes — added on filing. Spot-checks, not adjudication.

Three of the ruling's five named gaps are closable from material this project already holds. Doing so now because two of them change what the ruling *means*, and leaving them open until leg B lands would let a wrong reading settle.

### GAP-D — CLOSED, and it resolves in upstream's favour

The ruling asks whether upstream's 32-byte `statement_hash` covers `TransactionContextID`, and states that if it does not, §3.1's bug exists upstream masked only by the random salt.

**It does.** `src/proof_compact_standard.c` builds `stmt_hash` over `Pk_vec[0..n]`, `pk_A`, `C1`, `C2_vec[0..n]`, `PC_m`, `PC_b`, `B1`, `B2`, **then `context_id`**. The same pattern appears in `proof_compact_convertback.c`, `proof_compact_clawback.c` and `proof_pok_sk.c`. So upstream is protected **structurally**, not incidentally, and the salt is not what saves it.

Two things survive that, and both matter:

- **The element order matches the ruling's §1.6 Send row exactly.** An independent cross-check that the reviewer read Eq. 25 correctly.
- **`context_id` is optional at every call site** — the guard is literally `if (context_id)`, and `proof_pok_sk.c` documents it as `/* context_id is optional */`. A caller passing `NULL` reintroduces §3.1's bug in full. So the ruling's central mechanism is live *as a caller-error surface* even though upstream's own default is safe.

### GAP-C — CLOSED by execution, and §1.6's rows are the right rows

The ruling asks which proof format devnet rippled 3.3.0 accepts, and warns that if it is commitment-form, §1.6's table describes proofs the signer never builds.

**Compact form.** Three `ConfidentialMPTSend` transactions were accepted on Devnet on 2026-08-17 carrying `ZKProof` of exactly **946 bytes = 192 (compact sigma) + 754 (aggregated Bulletproof)**, and `Protocol.h` enforces that length at preflight (CLAIMS.md E-3, E-3a, E-4). A commitment-form proof at n=3 would be 196 bytes and would be rejected. **The table's rows are correct.**

### §5.4 — the citation correction is half right, and the other half is a new gap

The ruling is **correct** that, in the April 2026 report: there is no `RIPCTXR` series at all (zero occurrences); `TOB-RIPCTX-10` is *"Missing range proof enables confidential balance overdraft"*, High severity, not a brittle-API concern; `TOB-RIPCTX-17` is *"Missing input length validation in low-level cryptographic helper functions"*; and `TOB-RIPCTX-3`, *"Fiat-Shamir domain tag considerations"*, exists and is directly on point. **`TOB-RIPCTX-3` should be cited and is not.**

**But the packet was not citing the April report.** It was repeating upstream's own comment at `src/mpt_internal.h:199–201`:

> *"The TOB **May 2026 revision audit** (RIPCTXR-10, Informational) flagged the prior unprefixed layout as a brittle-API concern, not a present-day exploit"*

So upstream cites a **second, later document** with its own `RIPCTXR-` numbering. This project holds only the April report. **Neither the ruling's proposed correction nor the existing text is supported**: the reviewer's `TOB-RIPCTX-17` substitution is an inference — they say so themselves — and the original text attributed to the audit what should have been attributed to upstream's comment about a document we have never obtained.

**New gap: the TOB May 2026 revision audit is unobtained.** Recorded, not backfilled. Until it is read, the correct form of the claim is *"upstream's comment cites RIPCTXR-10 of a May 2026 revision audit"* — attributing the citation to upstream rather than asserting it ourselves.

### §3.1's mechanism — the crux — is confirmed

`TOB-RIPCTX-15` quotes the implementation directly: `addCommonZKPFields(s, txType, account, **sequence**, issuanceID)`. **The account sequence number is inside `TransactionContextID`**, and no statement point is a function of it. The ruling's exploitation path is mechanically sound on this point.

Appendix A's vectors are **verified**: reproduced by an independent TypeScript implementation written from the prose (T-2, zero mismatches), and the reviewer's own self-test reruns clean here — 3,960 single-bit mutations, zero collisions; framing injectivity; cross-type separation; purity; and four rejection paths.
