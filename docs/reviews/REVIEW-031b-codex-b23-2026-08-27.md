# Adversarial review — B-23 seed residue

Frozen commit reviewed: `0766d49317743f9fbf0f422af37246cadcbd8aa1`. HEAD matched and the tracked worktree remained unchanged.

Verdict: **defective**. The build still leaves decoded master-seed arrays unwiped, part 6 has concrete false-pass modes, and the status prose overstates completion.

## Findings

### HIGH — Decoded master-seed arrays remain unwiped on production paths

`REVIEW-029c` condition 2 explicitly puts “the decoded seed arrays” in scope, but four concrete bare owners remain:

- [`decode_ed25519_seed::out`](<$REPO/signer/src/xrpl.rs:1002>) is a bare `[u8; 16]` copied into the return value without wiping its source.
- [`decode_family_seed::out`](<$REPO/signer/src/xrpl.rs:1027>) does the same for secp256k1. The comment at lines 1029–1033 explicitly admits that the source remains live and unwiped.
- [`AccountKey::from_family_seed::entropy`](<$REPO/signer/src/xrpl.rs:474>) holds the returned array bare and never wipes it. This is the live profile-loading path through [`holder.rs:450`](<$REPO/signer/src/holder.rs:450>). `REVIEW-030b:1,7` had already reported this; it was lost before adjudication.
- [`looks_like_a_family_seed`](<$REPO/signer/src/onboarding.rs:263>) calls the same decoder and drops the successful `Result` payload bare through `.is_ok()`. It is reached for every onboarding argument at [`bin/onboard.rs:52`](<$REPO/signer/src/bin/onboard.rs:52>).

Only `keygen::derive_raw` handles its returned copy correctly: it wraps and explicitly wipes `entropy` at [`keygen.rs:239-251`](<$REPO/signer/src/keygen.rs:239>). That does nothing for the other consumers.

This is HIGH because it leaves the permanent master credential in post-lifetime stack residue and violates a mandatory ruling condition. P-5 still applies: fixing it narrows a window and removes no attack channel.

**What would falsify this:** make the decoder return a wiping `[u8; 16]` type constructed directly into its wrapper, with every consumer retaining that type until derivation/validation finishes; or explicitly wipe every source and caller-held array on success and error paths. A source/type gate must cover all four sites.

### MEDIUM — `check-zeroize-bounds` part 6 can false-pass

There are at least two independent attacks.

1. [`strip_line_comments`](<$REPO/tools/check-zeroize-bounds.py:502>) removes only `//` comments. A needle inside `/* ... */` still counts as production. Applying the exact stripping rule in memory to:

   `/* let raw = Zeroizing::new( */`

   produced a count of `1`. Thus the real wiping statement can be block-commented out while a bare replacement is used, and part 6 reports it present. The control at [lines 679–684](<$REPO/tools/check-zeroize-bounds.py:679>) tests only a `//` comment.

2. The “single decode” needle checks only the Ed25519 match arm at [`tools/check-zeroize-bounds.py:649-652`](<$REPO/tools/check-zeroize-bounds.py:649>). Replacing only the secp256k1 arm with:

   `AccountKey::from_family_seed(family_seed)`

   is type-correct and restores the second decode for secp256k1, while the Ed25519 needle remains present exactly once. The dispatch-agreement test also stays green because the account ID is unchanged.

The named-set caveat does not excuse either case: these are false passes inside a named property, not newly added unlisted sites.

**What would falsify this:** use token/AST-aware comment handling, add a block-comment control, scope the check to `derive_raw`, require both direct entropy arms, and reject any production `from_family_seed` call within that function. Mutation controls should exercise the secp-only revert.

### LOW — The `IgnoredAny` swap is not fully behavior-preserving, and the tests miss it

The old `serde_json::Value` parse materialized and semantically validated every value. The new scan at [`holder.rs:395-403`](<$REPO/signer/src/holder.rs:395>) uses `IgnoredAny`, whose locked serde implementation:

- skips arbitrarily large numbers without converting them to a representable JSON number;
- deliberately consumes `\u` escapes without validating surrogate pairing.

Consequently, a stale field such as `"balance":1e999` or `"balance":"\uD800"` formerly produced `ProfileError::Json` during the first `Value` parse. It now survives the name scan and produces `ProfileError::Stale`. Both versions refuse the profile, so the impact is error behavior rather than secret acceptance, but the repeated “behavior preserved” claim is false.

The three remaining tests have these bounds:

| Test | False-pass assessment |
|---|---|
| [`a_missing_seed_is_still_refused`](<$REPO/signer/tests/profile_parse_b23.rs:62>) | **Can false-pass for parser-error preservation.** An unrelated unknown-field error may contain `account_seed` in serde’s expected-field list. It does still robustly require some error rather than acceptance. |
| [`a_non_object_still_reaches_the_same_error`](<$REPO/signer/tests/profile_parse_b23.rs:73>) | **Can false-pass.** Making the map scan fail-fast returns its own `ProfileError::Json("invalid type … expected a map")`; the test passes although `RawProfile` was never reached and the error is not the same. |
| [`invalid_json_is_still_a_json_error`](<$REPO/signer/tests/profile_parse_b23.rs:83>) | **Sound only for its narrow assertion.** It proves rejection with the `Json` variant. It does not pin the message, producer, or general behavior preservation claimed by the file header. |

**What would falsify this:** add pre-swap expected errors for out-of-range numbers, invalid Unicode escapes, non-objects, and missing fields; assert the exact distinguishing error phrase or variant. Alternatively, explicitly accept the changed stale-field precedence and narrow the behavior-preservation prose.

### MEDIUM — Comments and status claims exceed the implementation

Several live sentences are false or materially incomplete:

- [`holder.rs:415-418`](<$REPO/signer/src/holder.rs:415>) says moving `p.account_seed` means “exactly one buffer exists.” At that point the zeroizing whole-profile `raw` buffer still contains the seed as well. At most, exactly one *deserialized account-seed allocation* exists.

**What would falsify this:** fix the unwiped arrays and then re-audit the named residual list, or qualify each sentence to the exact allocation/site it establishes.
