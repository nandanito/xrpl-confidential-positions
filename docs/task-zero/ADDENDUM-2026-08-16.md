Corrections to `TASK-ZERO-2026-08-13.md` after two sources surfaced that the original research missed: the Trail of Bits cryptographic review of April 2026, and the canonical xrpl.org documentation page, last updated roughly two weeks ago.

**Read this before Session 1.** It invalidates part of §9, retires two findings, and adds a hard constraint that changes the domain design.

## 1. The constraint that changes the design

**TOB-RIPCTX-1 — ElGamal decryption is bounded at 1,000,000 units.**

Encryption accepts any 64-bit unsigned integer. Decryption recovers the plaintext by brute-force discrete log, and the loop runs to 1,000,000. Above that the ciphertext is mathematically valid and **permanently undecryptable through the provided API**. Trail of Bits records the exploit path plainly: an account holding 500,000 that receives transfers totalling 600,000 ends up with a valid, unreadable balance, with no signal at encryption time that the threshold would be crossed.

**Fix status: Resolved, but the practical limit stands.** The routine was renamed `secp256k1_solve_dlp_small_range_ct` and the hard-coded bound became a `max_range` argument — and Trail of Bits notes in the same paragraph that the caller still passes a magic number of 1000000.

**This breaks §9 as written.** The restructured facility has the bank's vault convert the entire float in a single `ConfidentialMPTConvert`, and the worked example uses 10,000,000 units. That balance would be undecryptable the moment it was created. The vault could not read its own balance, and could not generate a send proof, because proving requires knowing the plaintext.

Three consequences, none of them optional:

- **The facility float must stay under 1,000,000 units**, or be split across several vault accounts, or rely on `AssetScale` so the raw integer stays bounded while the displayed denomination does not. Whether `AssetScale` genuinely helps needs checking — the limit applies to the raw integer the ciphertext encodes, so scale is a presentation choice that may or may not move the ceiling in practice.
- **Accumulation is a live failure mode for holders, not just the vault.** A supplier receiving many drawdowns can cross the threshold through ordinary use and silently lose access. Any application built on this needs a balance ceiling and a warning well before it.
- **The observer harness gains a test**, and the onboarding warning gains a fourth item alongside the three irreversibilities already recorded.

**Grade A.** Read from the audit and the quoted source loop. Confirm the current caller value against `mpt-crypto` at the pinned version during Session 1 Task 2, since that session is already reading those headers.

## 2. Two findings retired — and a near-miss worth recording

The RippleX prerelease documentation at opensource.ripple.com has been superseded by the canonical page at `xrpl.org/docs/concepts/tokens/fungible-tokens/confidential-transfers`. Two of the four documentation errors in §8 no longer exist.

**F-3 retired.** The prerelease docs said the privacy setting could be toggled on and off. The canonical page now states that enabling the flag is *"a one-way operation: no subsequent transaction can disable it."* Corrected upstream. Nothing to file.

**F-4 retired, and this is the important one.** The prerelease docs said clawback resets the version counter to 0. That was not a documentation error — it was **TOB-RIPCTX-11, a Medium-severity implementation bug found by Trail of Bits in April 2026 and since Resolved.** The docs were describing real pre-fix behaviour. The canonical page now says the counter increments, matching rippled 3.3.0.

Had U-3 been filed as written, it would have reported a bug the RippleX team's own auditors found four months earlier and had already fixed. That is precisely the failure the feedback register's evidence bar exists to prevent, and the bar did not catch it, because the register checked the claim against the specification and the implementation but not against the audit.

**New standing rule, added to `UPSTREAM-FEEDBACK.md`: nothing is filed without first checking the Trail of Bits report and the fix-review appendix.** Seventeen issues are already known and fourteen are resolved. The remaining space for novel findings is narrow, and anything inside it needs to be checked against that report before it goes anywhere near the RippleX team.

**F-1 survives, and is now stronger.** The canonical page still says the post-merge inbox reset value *"is a valid ElGamal ciphertext that represents zero, but is indistinguishable from other ciphertexts to observers without the private key."* That sentence is self-contradictory: deterministic means recomputable from public inputs, which means distinguishable. The separate statement under Privacy Properties — that balances which reach zero through transfers are indistinguishable from non-zero balances — is correct, because those ciphertexts are randomised. The error is the generalisation of the second to the first. It is not in the Trail of Bits report, and it is now on the canonical page rather than a prerelease one.

**F-2 reframed.** The canonical page describes issuer-mediated auditing accurately, including that it *"grants the auditor the same decryption capabilities as the issuer."* The divergence is therefore a specification erratum only — §13.2.2's "separate set of view keys" has no corresponding ledger field — not a documentation error. **F-5 and F-6 are unaffected**, though F-5 likely falls inside TOB-RIPCTX-14, *"Discrepancies between specification fields and implementation,"* which is marked **Partially Resolved**. Check before filing.

## 4. New information from the canonical documentation

- **Recommended clawback flow.** Lock the holder's MPT with `tfMPTLock` *before* submitting `ConfidentialMPTClawback`, otherwise the proof can go stale between generation and validation and the transaction fails on-ledger. Not in the specification text as read.
- **A new trap.** If an issuer declares the Can Hold Confidential Balance flag immutable without enabling it, that issuance can never support confidential transfers. Interacts with Mutable MPTs (XLS-94).
- **Version counter increments on all four of** send, merge, convert-back, and clawback.
- **Keys can only be registered via `MPTokenIssuanceSet`**, so an issuer who sets the flag at creation must follow up with a second transaction before any holder can convert.
- **The documentation states plainly that the scheme is not quantum-safe**, and that migration to post-quantum primitives *"remains an open area of research."* That is canonical support for W-PQ's W2 workstream addressing a genuinely open question rather than a solved one — cite the page, not an inference.

## 5. The network question — still open

The confidential faucet URL in the earlier documents came from the prerelease docs and appears to be dead. **It has been removed from the tooling.** The canonical page names no dedicated network and no faucet; it renders a live amendment-status widget instead.

It is plausible that `ConfidentialTransfer` is now votable or enabled on standard Devnet, which would simplify everything. **It has not been verified, and it must not be assumed.** This is GAP-1 unchanged, and it is exactly what Session 1 Task 1 exists to settle. `tools/check-amendments.ts` now queries mainnet, testnet and devnet, with the guessed confidential-devnet endpoint removed rather than left in to produce a misleading "unreachable" result.

Three amendments still need to be enabled together for the full scope: `ConfidentialTransfer`, `PermissionedDomains` and `SingleAssetVault`.

## 6. The lesson worth keeping

The research in `TASK-ZERO-2026-08-13.md` was three days old when two of its six findings went stale and a third turned out to be a known, fixed, audited bug. The BLOCK 0 briefing sets a 30-day shelf life on verified claims. **For a Draft specification under active remediation, 30 days is far too long.** Re-verify before any claim is published or filed, not on a calendar.

The specific gap in method: the original research covered the specification, the implementation and the documentation, and never asked whether the code had been audited. For anything cryptographic, the audit is a primary source and should be sought in the first pass, not the fourth.
