## 1. rippled — issue #4, and the answer is that the defence holds

**Question.** Does the registration verifier pass a non-NULL `context_id`? If it
does not, `CMPT_POK_SK_REGISTER` binds only `pk`, and a registration proof is
**copyable to another account** — which would make ADR-0001 §(b)'s rogue-key
defence weaker than the ADR claims.

**Answer: it passes a non-NULL `context_id`, the context binds the account, and
the proof is copyable nowhere.** Five links, each read at source:

1. **`ConfidentialMPTConvert::preclaim`** — `src/libxrpl/tx/transactors/token/ConfidentialMPTConvert.cpp:153–162`.
   When the transaction carries `sfHolderEncryptionKey`, it computes
   `getConvertContextHash(account, issuanceID, ctx.tx.getSeqProxy().value())`
   where `account = ctx.tx[sfAccount]` (line 74) — the **submitting** account —
   and passes the result to `verifySchnorrProof`.

2. **`verifySchnorrProof`** — `src/libxrpl/protocol/ConfidentialTransfer.cpp:366–375`.
   Calls `mpt_verify_convert_proof(proof.data(), pubKey.data(), contextHash.data())`.
   `contextHash` is a stack `uint256`; `.data()` cannot be NULL.

3. **`mpt_verify_convert_proof`** — mpt-crypto `src/utility/mpt_utility.cpp:859–883`.
   **Rejects a NULL context hash outright** — `if (!pubkey || !context_hash || !proof) return -1;`
   — then forwards it to `secp256k1_mpt_pok_sk_verify`. The utility layer, which
   is the layer rippled links, makes the binding **mandatory**.

4. **`build_pok_challenge`** — mpt-crypto `src/proof_pok_sk.c`. The Fiat–Shamir
   challenge is `SHA-256("CMPT_POK_SK_REGISTER" ‖ pk(33) ‖ T(33) ‖ context_id(32))`,
   reduced to a scalar. All fields fixed-width, so the preimage is unambiguous
   without explicit framing.

5. **`mpt_get_convert_context_hash`** — mpt-crypto `src/utility/mpt_utility.cpp:349–369`.
   Builds `sha512_half( u16(kCONFIDENTIAL_MPT_CONVERT) ‖ acc(20) ‖ iss(24) ‖ u32(seq) ‖ acc(20) ‖ u32(0) )`.
   The account appears **twice** — once via `mpt_add_common_zkp_fields`, once
   appended directly.

**Consequence.** The registration proof is bound to the triple
**(account, issuance, sequence)**. It is not copyable to another account, not
replayable against another issuance, and not replayable by the same account at a
different sequence. §(b)'s rogue-key claim is **not** weaker than stated; if
anything the ADR undersells it, since it describes only the rogue-key property
and not the account binding. → `CLAIMS.md` **E-66**.

**But the library API below rippled does not enforce this.**
`secp256k1_mpt_pok_sk_verify` treats `context_id` as optional — `/* context_id is optional */`,
and `build_pok_challenge` folds it in only `if (context_id)`. Passing NULL
produces a proof over `pk` alone: valid, account-unbound, and copyable by anyone
who has seen it. The **public header** `include/secp256k1_mpt.h:219–224` declares
the parameter with **no doc comment at all** — no mention that NULL is accepted
or what it costs. Nothing on the rippled path can reach this, but any other
consumer can: a Rust or WASM binding, or our own signer's test harness.
→ `CLAIMS.md` **F-19**, `UPSTREAM-FEEDBACK.md` **U-38**.

**Issue #4's three questions, answered:**

- *Ordered element list of the Fiat–Shamir preimage:* `"CMPT_POK_SK_REGISTER" ‖ pk ‖ T ‖ context_id`.
- *Do `AccountID` and `MPTokenIssuanceID` bind in?* **Yes, both**, through `context_id`.
- *Is a `TransactionContextID` present?* Yes — the Convert context hash, which is
  the same construction the other transaction types use, and it includes the
  sequence.

## 2. XLS-0096 — B-12, and the answer is silence

**Question.** Does the specification anywhere state that the ElGamal encryption
randomness `r` must not be reused across transactions?

**Answer: no. The specification is silent, and that is a specification gap.**

Checked against the full 971-line text. What the spec *does* say about `r`:

- **§5.4** is the only place the word "reuse" appears in connection with
  randomness, and it points the **opposite** way: the `AmountCommitment`
  *"intentionally reuses the ElGamal ciphertext randomness as its blinding factor
  rather than introducing an independent scalar."* That is deliberate reuse
  **within** one transaction. Read quickly, it reads as permission.
- **§7.2 / §10.3** describe `BlindingFactor` as *"the 32-byte scalar value used to
  encrypt the amount"* — no sampling requirement, no freshness requirement, no
  distribution requirement.
- **§7.3.1 / §10.4.1** failure conditions check **length** (`temMALFORMED` unless
  exactly 32 bytes) and **consistency** with the submitted ciphertexts
  (`tecBAD_PROOF`). Nothing rejects a repeated value, and rippled 3.3.0 stores no
  state that would let it. Confirmed at
  `ConfidentialMPTConvert.cpp:179` and `ConfidentialMPTConvertBack.cpp:80`: the
  field is read and handed to `verifyRevealedAmount`, and that is all.
- **§13.8 "Attack Surface & Mitigations"** enumerates replay, malformed
  ciphertexts, balance underflow, auditor collusion and issuer misbehaviour.
  **Randomness reuse is not among them.**
- **§A.7 "What prevents replay or proof reuse?"** answers about *proof* reuse via
  transcript binding. It does not address randomness reuse, and the section title
  makes it the place a reader would look.

**This is a grep plus a directed read, and it is proving a negative.** The
searches covered `reuse`, `re-use`, `reused`, `fresh`, `random`, `randomness`,
`blinding`, `nonce`, `entropy`, `CSPRNG`, `unique`, `distinct`, `unpredictab`,
`independent scalar`, `per-transaction`, `each transaction`, and `MUST`, and
§§5.4, 7, 10, 13 and Appendix A were read directly. A statement using vocabulary
none of that reaches would not have been caught.

**Consequence for U-37.** B-12 said the answer decides U-37's shape: silence
makes the specification gap fileable on its own; a statement would shrink the ask
to a library doc-comment. **It is silence**, so U-37's stronger form is unblocked
on this axis — with the standing caveat that nothing moves out of `Observed` in a
coding session. → `CLAIMS.md` **E-67**.

**Also worth having:** the spec calls the issuer-controlled holder account a
**"Dedicated Account"** and notes at §3 and §13.5 that it *"is sometimes called
the 'Confidential Vault'."* Our convention — say Dedicated Account, never vault —
matches the spec's own primary term.

## 3. Trail of Bits May 2026 revision audit — a named gap, not a substituted source

**Not obtained, and the negative result is stronger than "we looked and failed."**

`github.com/trailofbits/publications/tree/master/reviews` is the primary source
and it is **current**: 448 reports, including sixteen dated 2026-05 through
2026-08. It is not lagging. It contains **exactly one** Ripple report —
`2026-04-ripple-labs-xrp-ledger-confidential-transfer-securityreview.pdf`, the
April report already on disk at `docs/references/`. There is no May revision
report under any name. A web search returned only secondary coverage of the April
report and nothing about a revision.

**Conclusion: the revision audit is not publicly published.** It is recorded as a
gap. It is **not** backfilled from blog coverage. → `CLAIMS.md` **B-13**.

**What is nonetheless now known about its contents**, from the only citable
source — comments in mpt-crypto at the pinned commit. This bounds the gap instead
of leaving it unknown:

| Finding | Where cited | What upstream says it is |
|---|---|---|
| **TOB-RIPCTXR-1** | `include/secp256k1_mpt.h:42–43` | TOB-RIPCTX-1 / -4 (amount-dependent timing side channels in the decryption search) **reintroduced**. Mitigated by a fixed-iteration search |
| **TOB-RIPCTXR-10** | `src/mpt_internal.h:188, 199–201` | **Informational.** The prior unprefixed nonce-KDF IKM layout flagged as a brittle-API concern, *"not a present-day exploit"* |

**Two conclusions follow, and one of them corrects an expectation this session
was handed.**

1. **On present evidence the revision audit does not bear on keygen.** Both
   citable findings are elsewhere: RIPCTXR-1 is decryption timing, RIPCTXR-10 is
   nonce-KDF preimage framing. Neither is key derivation, and neither is
   randomness *sourcing*. The keygen packet should not wait on this document.
   Two identifiers out of an unknown total is not the whole report, so this is a
   statement about what we can see, not about what the report contains.

2. **It cannot settle the `context_id`-optional question, and does not need to.**
   That was answered directly from source in §1 above, which is the better
   outcome — a primary reading rather than a citation.

**A convergence worth recording.** RIPCTXR-10's concern is that an unframed IKM
lets two call sites with different witness packings construct the same preimage
from semantically distinct inputs. Both W-CONF randomness rulings adopted
`u32be` length framing before every variable-length field, independently and for
this reason. The W-CONF nonce patch **replaces** upstream's
`generate_deterministic_nonces` entirely, so it is worth stating that it does not
regress the finding: `wconf_generate_nonces` frames every field inline —
`"WCONF-NONCE-v1" ‖ u32be(k) ‖ u32be(domain_len) ‖ domain ‖ u32be(witness_len) ‖ witness' ‖ u32be(stmt_len) ‖ stmt ‖ u32be(ctx_len) ‖ context_id`
— which is stricter than upstream's 16-byte fixed preamble, not weaker.
